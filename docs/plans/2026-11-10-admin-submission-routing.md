## 操作规则

管理员手工新增或通过 Excel 录入时保存实际录入人、来源、学期、周次和检查类型。提交去向在首次提交成功时确定。已有管理员未提交草稿也适用。

有相应提交权限的管理员打开提交抽屉，选负责该类型的部门或管理员通道，都能勾选本人同一学期、周次、类型下未删除、未提交且未锁定的草稿。部门候选沿用有效配置。候选资格按每条记录判定，支持从同一导入批次分次选择。普通管理员按有效业务权限操作，超级管理员沿用现有全局授权。

列表查看按检查类型及有效个人范围。委员能看到授权类型下其他人和管理员录入的记录，只能凭录入权操作本人合格草稿。管理权仍可操作授权范围内的合格记录。新增的双通道选择仅针对管理员自己的草稿。

两个通道共用待审核、退回、原批次重提、确认流程。具备该批次审核权的管理员允许自审，需明确执行确认操作。确认后按原检查类型、周次及相同统计规则汇总一次，保留提交去向以便追溯。

## 普通成员与学生会办公室（日常检查八类页面）

- 普通业务成员提交时只读显示账号主部门（例如学习部），由后端核对该部门负责所选检查类型。缺少有效映射时禁止提交。候选、Excel、实际提交及零记录回执都须执行同一范围校验。修复前八页共用的抽屉使用查看范围选项，显示了管理员；部分查询又将请求静默改为主部门。改为服务端对不匹配的目标明确返回 403，合法的主部门候选可正常分页。
- 学生会办公室成员（委员、部长、副部长、主席团成员）在日常检查只读查看有效查看范围内、已由相应通道确认的记录。服务端依据可信部门身份限制列表、详情、批次及导入相关读取，草稿、待审和退回数据不可从旁路读取。检查写操作在服务端拒绝，包括新增、导入、编辑、删除、提交及审核。页面仅显示获准的查看操作。该规则作用于日常检查源记录，办公室在通报模块的授权按原业务处理。
- 代码核查：八页使用同一提交组件，组件内部直接绘制提交按钮。创建和审核等操作各有权限条件，不能据此断言每个办公室账号均已看到全部按钮。通用权限计算按部门映射和个人授权生成动作；修复前日常检查列表没有按 OFFICE 强制执行仅已确认来源的约束。验收时逐页核对办公室各角色以及直接 API 请求，并对照普通业务委员仍可查看类型范围内草稿。
- 候选接口 500 单独回归：全零 UUID 是界面“管理员”的传输值。成员通过前置鉴权后，handler 用主部门查询；测试须分别请求全零值和合法主部门，且主部门下必须至少有一条本人可提交记录。修复前 inspectionColumns 投影遗漏 class_name_snapshot，而 Read 仍扫描 ClassName 和 ClassID，详情读取列数不匹配。修复投影并断言候选的班级名称和 ID；无记录返回空页，越权返回 403，内部错误仍保留为 500。

修复前在一次性 PostgreSQL 上执行 `go test ./internal/store -run ^TestInspectionPostgresCRUD$ -count=1`，实际失败并复现共用读取错误：查询返回 26 列，Scan 要求 27 列。尚未使用反馈账号重放浏览器原请求。该测试另报年级名称重复后缀和重复记录错误，须分别核对。

用户补充现场证据：同一委员、学期、周次、到课率检查类型及分页，分别传入全零 UUID 与部门 `10000000-0000-0000-0000-000000000002`，均收到 HTTP 500 / `INSPECTION_FAILED`。验收需独立重放两条 HTTP 请求：合法主部门有本人草稿时返回 200 并包含该记录及正确班级字段；委员显式选择管理员通道返回 403 / `FORBIDDEN_SCOPE`。

## 实施顺序

1. 先在一次性 PostgreSQL 用虚构管理员创建 A、B 两条草稿，重放实际候选查询和提交请求，记录修改前失败点。分别覆盖普通管理员和超级管理员。
2. 在批次上明确保存提交去向。用只追加迁移将记录的录入来源与已绑定的提交范围分开，使管理员草稿可绑定到具体部门。数据库继续约束提交批次、学期、周次、类型及提交范围的一致性。兼容已有部门和历史校级批次、零记录回执、原批次重提以及不可变修订。
3. 手工候选、Excel 批次计数和明细、提交事务及幂等重试采用一致的逐条资格判断。提交时在同一事务内复核权限和版本、锁定记录、绑定批次、写修订和审计。两个通道并发选同一草稿最多成功一次。
4. 提交抽屉沿用“选择去向 → 勾选记录 → 确认”顺序，确认页展示实际去向。提交成功刷新两个通道的候选、导入批次和审核列表。退回后在原批次处理。周汇总及通报读取当前已确认修订，按检查类型计入，区分历史校级来源。
5. 同步 PRD、技术方案和项目状态。完成后运行后端 vet、完整 Go 测试及并发回归，前端 lint、完整测试及构建，并使用隔离真实 API 和浏览器重放下述场景。

## 验收

- 同一管理员的 A、B 在两个通道都可见。A 交给负责部门后，两个通道均只剩 B。B 走管理员通道后，两个批次分别进入待审核。
- 分别覆盖手工、Excel 和已有管理员草稿。拒绝不负责该类型的部门、超出有效权限的操作及重复提交。并发冲突整批回滚，响应丢失后重试返回原批次。
- 委员能查看同类型的他人记录，不能提交他人的管理员草稿。有审核权的管理员能自审，只有提交权的管理员不能审核。退回、修改、重提沿用原去向和修订历史。
- 两条记录属于同周同类型，未确认时均不计入默认通报；两条依次确认后，记录计数依次增加一条。核对统计字段、批次来源和历史版本，而非仅检查列表行数。


## 本地验收记录

- 新增 051 迁移。录入人、录入部门与来源保留；首次提交在事务内绑定去向，外键校验提交批次范围。历史校级批次保留标识。
- 一次性 UTF-8 PostgreSQL 验证真实投影、两个候选范围、普通管理员自审及两种已确认来源按原类型读取。已确认导入批次的 Excel 草稿在两个去向均计入可选数量。
- Chrome 156 隔离联调（真实 API 与 PostgreSQL）重放到课率候选。学习部委员在本人有草稿时查询本部门返回 200，班级正确；全零 UUID 返回 403 / FORBIDDEN_SCOPE。学办读取草稿、待审记录均返回 404，确认后可见。页面验证委员归属锁定为学习部。学办委员、部长、副部长和主席团成员四种职务即使有单独授予的检查写权限，也无法读取待审批次或确认该批次；逐一打开八类检查页面，均无新增、导入、编辑、删除和提交审核入口。
- 浏览器专项命令为 `BROWSER_DB_MODE=native BROWSER_SUITE=submission-routing python3 server/scripts/verify-browser.py`。检查使用虚构账号、学期和周次。Excel 已确认导入批次的路由和记录级提交已在数据库回归中验证；本轮浏览器没有重新执行文件上传至解析入库的完整链路。
- 最终核对弹窗曾和提交抽屉处于同层。真实浏览器回归先观察到层级断言失败；弹窗改为在所属抽屉中渲染后，在 390px 与 1280px 窗口分别核对按钮中心接收指针，取消保留清单，再次打开并点击后真实 POST 返回 201。批次退回、确认和重提对话框沿用同一嵌套方式。
- 检查结果：后端 vet、完整 Go 测试与 race 通过；前端提交组件 11 项、lint（1 条既有警告）、build 通过。默认串行完整 Vitest 运行中有 1 项学期日历可见性断言失败，该项单独重跑通过。另一次并行尝试出现多项 10 秒超时。旧 department-submission 浏览器脚本停在创建管理员记录时选择“目标部门”的历史步骤；本轮提交与权限专项使用 submission-routing 实测通过。
