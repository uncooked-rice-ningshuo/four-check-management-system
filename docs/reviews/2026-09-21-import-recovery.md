## 本项实现

- 错误预览或已解析失败批次提供“重新上传文件”，二次确认说明原批次和审计保留；重传清空文件、错误、分页、筛选和确认状态，重新走新批次上传。不会取消、删除或直接修改旧批次。
- 确认弹窗展示检查类型、学期、周次、部门业务名称及草稿数量。恢复的批次按自身范围查找名称，不误用当前列表筛选；范围信息缺失时明确报错并禁止确认。
- 同一批次/版本的确认重试复用幂等键，发送首次确认时锁定的版本；后台刷新不静默替换用户确认过的版本。真实 409 后刷新批次，重新核对后再提交。
- 确认进行中禁用弹窗/抽屉关闭与取消；已确认批次的结果可重新展示，避免恢复时只剩流程步骤而没有结果提示。

接口和数据库结构未变，重传使用已有上传 API，确认使用已有版本和幂等契约；未增加依赖、执行目标库发布或替换业务服务。

## 测试与证据

新增组件/Hook 回归先观察失败：缺少重传入口、确认范围使用 ID、临时失败重试幂等键变化、版本冲突后批次未刷新。修复后聚焦覆盖恢复旧周次、范围缺失、处理中/已确认不可重传等边界。

真实 E2E 继续沿用 `server/scripts/verify-browser.py`，新增 `web/e2e/import-recovery.js`：

1. 错误文件上传→仅错误筛选→重传取消→确认新批次→修正文件预览，旧文件和筛选不残留。
2. 确认弹窗检查业务名称；将请求版本改为 999999 后由真实 API 返回 409，刷新后允许重新确认。
3. 真实 API 成功提交，但将浏览器响应替换为 500；同键重试返回成功，列表只增加两条。
4. 直接核对隔离 PostgreSQL：原错误批次仍为 PREVIEW_READY、零业务记录；修正批次两条记录、一条确认审计。

最初新增套件重载相同 URL 恢复了上个套件未完成批次，导致底层按钮被抽屉遮挡；这是预期的批次恢复行为。独立场景改为从工作台进入，未通过关闭产品恢复能力让测试通过。
