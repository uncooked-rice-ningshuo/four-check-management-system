# 通报工作台按检查类型汇总改造方案

- 日期：2026-11-01
- 状态：本地实现与隔离验收完成；目标业务环境部署、真实账号角色验收仍待执行。
- 适用范围：通报工作台三个阶段、通报归档版本详情，以及对应的汇总、版本记录查询和溯源展示。优先于旧文档中“部门/校级范围 → 检查类型”的页面组织描述。

## 1. 决定与边界

每周仍只有一份合并通报。工作台和归档版本详情以当前参与通报的检查类型作为第一层组织；每类聚合所有有权查看的部门及校级来源。部门/校级归属不作为首页主分组或版本标签，但保留在单条记录的来源详情、按需筛选、提交批次明细、应交异常清单、权限校验及审计中。

“八类”是页面组织维度，不代表八类都已接入完整提交与验收。类型列表从启用且参与通报的配置读取；暂停专项开发的类型不能伪装为“已确认零条”。不增加一级导航：仍只有通报工作台和通报归档。

本次不取消部门/校级提交批次、逐周应交单元、零记录回执、整份报告的版本和状态机；不改已生成版本的不可变内容，也不改变 Word/Excel、发布或正式统计指标的既定待办。

## 2. 页面与交互

### 阶段一：确认来源数据

- 主表每行一个检查类型，按配置顺序展示。列为：检查类型、提交批次、待审核批次、退回批次、已确认批次、已确认业务记录、已确认零记录回执、应交异常数及“查看提交与记录”。各计数是当前授权范围内该类型所有来源单元的和；汇总总数不得重复求和同一批次或记录。
- 点“查看提交与记录”打开抽屉，默认展示该类型各单位提交批次及状态，再查看批次中的确认记录；提供提交单位筛选。记录列表仍按类型展示业务字段，单条详情显示来源归属、提交批次、实际提交人和时间、确认修订及核对所需的业务详情。没有真实历史值时显示“历史信息未保存”，不回填当前组织或人员名称。
- 另设简洁的“待完成应交项”区域，逐项列出单位、类型和缺失/草稿/待审核/退回状态。零记录回执只证明对应应交单元已确认零条，不计业务记录。来源明细和异常清单不得把无批次、未接入、无权限或加载失败显示成零条。
- 生成草稿仍只引用已确认来源；未完成应交单元仍默认阻止生成。强制生成须单独权限、理由和审计，不能因页面合并计数而跳过。

### 阶段二：编制和修订草稿

- 当前版本的主表/标签按检查类型展示本版记录数、零回执数和明细入口；单条记录按类型展示首屏重要字段和完整详情。默认不在每行重复显示校级/部门分类标题。
- 明细可按提交单位筛选，并保留现有个人字段筛选仅用于适用类型。修正、排除、恢复和读取最新来源仍生成新版本并保留审计。来源归属与提交人属于溯源元数据，办公室修正只修改允许的通报业务字段，不得改写来源提交事实。
- 版本历史先展示版本号、时间、状态与总数；展开所选版本后按检查类型查看当时的冻结记录。新版本不能改变旧版本内容。

### 阶段三：确认定稿数据及归档

- 待审核和待定稿版本沿用阶段二的类型分类和明细；审核、退回、定稿仍在固定底部操作区，定稿需二次确认并说明固定的是哪一版结构化数据。
- 归档保持按周次查询；所选版本的明细抽屉按检查类型切换。只读记录详情同样展示来源溯源。归档仍包含所有已生成过草稿的周次，不能因未定稿而隐去。

## 3. 数据口径、接口和历史兼容

1. **聚合口径**：服务端保留现有“学期/周次 × 部门或校级 × 检查类型”来源单元与应交状态，新增按类型的授权聚合视图/查询。记录分页、筛选、总数必须在数据库中按检查类型与有效权限执行；不能先把全量敏感记录传给前端合并。
2. **提交与确认分开**：批次数按批次及其当前状态计，已确认记录按该类型可纳入的确认记录计；零回执单列。待审核/退回记录不得混进通报版本。应交异常仍按原始单位 × 类型判断，并提供对应单位的详细入口。
3. **版本与权限**：新查询可按 `inspectionTypeId` 跨来源分页，不要求 `departmentId` 或 `collegeLevel`；可选的提交单位筛选只缩小结果。仓储 SQL 逐行按有效 `REPORT_VIEW`/`ARCHIVE_VIEW` 与版本可见规则过滤。现有完整版本不可被部分授权账号读取的边界保持；不得靠前端合并绕过。
4. **溯源字段**：版本记录已有 `source_submission_id` 与 `source_revision_no`。新明细响应需明确区分 `sourceDepartmentId`/`sourceDepartmentName`（校级用显式标志）、`sourceSubmissionId`、`sourceRevisionNo`、`submittedByName`、`submittedAt`，必要时提供确认时间。服务端只返回安全的显示名称，不输出内部对象 key 或无权限信息；个人信息按最小必要展示。
5. **历史版本**：业务字段继续从不可变 `included_data_json` 读取。既有版本的来源 ID/修订可用于追溯；如果当时没有冻结提交人、单位名称等显示值，旧版详情须标明其历史值不可用或为当前名称，不得将当前名称直接称为“当时提交名称”。新版本应冻结必要的溯源显示字段；具体存储方案实施前先核对现有批次修订快照，若不足，使用只追加迁移或新版本快照字段，不改写旧版本。
6. **失败行为**：聚合接口、明细接口、筛选项和来源关联读取失败应显示可重试错误，不能返回成功空态；越权维持 403/404 策略。分页总数、筛选候选项与实际结果使用同一授权和版本范围。

## 4. 改动范围

| 层面 | 改动 | 保留 |
| --- | --- | --- |
| 页面 | 工作台第一阶段的部门树改为类型表；草稿/定稿及归档版本标签改为类型；提交批次抽屉、来源筛选和单条溯源展示；窄屏与固定底栏适配 | 两个导航入口、三个阶段、按类型业务字段、版本审计 |
| 前端契约 | 类型汇总、跨来源分页及来源元数据类型与 Query hook；筛选状态在版本/类型切换时重置 | 现有 HTTP Client、权限入口与通报状态流 |
| 后端 | 类型聚合与跨来源分页 SQL、权限过滤、来源关联投影、必要的历史显示兼容 | 部门/校级提交、应交配置、零回执、草稿生成与定稿状态机 |
| 数据库 | 先核对既有来源修订快照；仅在无法保存新版本历史溯源显示值时追加迁移 | 已应用迁移和既有报告版本均不回写 |
| 文档/测试 | 同步 PRD、页面梳理、技术方案和状态；覆盖类型计数、跨单位分页、零回执、缺交、部分授权、历史版本、失败重试及真实浏览器交互 | Word/Excel 模板和发布规则仍单列待办 |

这是跨前后端的中等规模改造，不能只将现有表格在浏览器中重新分组。先完成聚焦测试及实际 PostgreSQL 权限/分页回归，再运行前后端完整检查；最后用隔离真实 API 与浏览器覆盖三个阶段、归档、八类适用字段、窄屏和角色矩阵。业务目标环境是否加载应单独验收。

### 本地实现记录（2026-11-01）

- 工作台来源表、当前版本表、版本历史及归档版本页已按检查类型展示；来源抽屉保留逐单位提交/应交明细，记录列表和详情显示提交归属、提交人、时间及修订。跨来源记录查询与版本记录分页在服务端按权限和类型执行。
- 来源与版本的类型计数由前端对服务端已授权、完整返回的单元行求和；尚未提供独立的服务端类型聚合接口。后续若单元行改为分页，须先将聚合移到服务端，不能对单页求和。单条来源名称、提交人姓名明确标为当前名称；本轮未冻结新版本的历史显示名称，因此不应将其解释为提交当时名称。
- 隔离 PostgreSQL 工作流回归、Go 全量检查、前端 83 文件/459 项测试、lint、类型检查和构建通过；一次性 PostgreSQL/MinIO + 真实 API/Vite + Chrome 156 的 28 项浏览器场景通过，包含工作台三阶段、跨来源汇总、修正、归档和窄屏。目标环境未加载本轮代码，模板/Word/Excel 输出仍未交付。

## 5. 实施顺序和完成条件

1. 先为当前未完成的八类布局/倍数快照增量补齐完整测试与已登录浏览器回归，确认现有基线；修复发现的问题。
2. 实现服务端按类型授权聚合、跨来源版本记录查询和溯源字段，并用一次性 PostgreSQL 验证计数、分页、权限、失败路径和旧版本兼容。
3. 替换工作台三个阶段及归档的分类视图，接通来源筛选、批次/记录详情和应交异常入口；同步前端契约、测试与设计文档。
4. 隔离浏览器验收首次进入、版本切换、修正后新版本、待审/零记录/缺交、部分权限、归档、失败重试、窄屏与底部操作。再核对目标环境迁移、加载和真实角色，未加载前只标记“代码已实现”。

完成判定：页面首层不再按校级/部门拆分；同一类型跨来源的数和分页明细一致；每条记录可追溯真实来源提交；缺交仍能定位到单位与类型；越权不会因聚合暴露记录；旧版本保持不可变；本轮适用检查和真实浏览器回归通过。
