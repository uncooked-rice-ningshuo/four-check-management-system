# 刷新响应丢失恢复协议方案

**状态：调查完成，等待安全语义确认。** 本文记录现状与备选方案，不是已批准的实现规格；本次没有修改认证运行时代码、数据库结构或 Cookie 行为。

## 已核对的现状

1. 登录和刷新使用 32 字节随机不透明 Refresh Token。数据库 `refresh_sessions` 仅保存 Token 哈希；浏览器通过 `HttpOnly`、`SameSite=Lax` Cookie 持有原文，Cookie 路径限定在 `/api/v1/auth`。
2. 刷新先读取会话与账号、准备 Access/Refresh 凭据，再由 PostgreSQL 事务锁定账号并原子消费旧会话、插入新会话。事务成功后，HTTP 响应才带回新 Access Token 和替换后的 Cookie。
3. 当前前端把同一 JavaScript 运行时的启动恢复和并发请求合并为一次刷新；网络错误或 5xx 保留页面会话并可重试。刷新明确返回 401 时会清除本地会话。
4. 一次性 PostgreSQL 测试覆盖了会话插入失败回滚、失败后使用原 Token 重试成功、成功轮换后的旧 Token 再用被拒，以及两个并发刷新仅一个成功。
5. 已有受控浏览器证据表明：若数据库轮换已经提交但响应未到浏览器，浏览器仍持有旧 Cookie；随后刷新被服务端拒绝并返回登录页。整页导航的历史自然复现另有诊断记录：[认证刷新整页跳转诊断](../reviews/2026-09-21-auth-navigation.md)。

## 必须保持或明确改变的约束

- 账号禁用、改密或会话版本变化后，旧刷新凭据不能恢复有效。
- 同一旧会话不得创建多个后继会话；并发请求必须有唯一胜者或明确的同操作幂等结果。
- 不在数据库、日志或浏览器可读存储中保存未保护的 Refresh Token 原文。
- 服务端无法仅凭事务提交判断浏览器是否收到响应。若仍要求旧 Token 绝不再次被接受，响应丢失后的透明恢复无法由客户端单独实现；保留严格单次消费就意味着极少数此类故障需要重新登录。

## 备选方案

| 方案 | 行为 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| A. 保持严格单次消费 | 维持当前协议；轮换已提交但响应丢失时，旧 Token 失效，用户重新登录 | 不扩大旧 Token 的可用范围；无需迁移 | 保留已知的意外退出体验 |
| B. 只增加浏览器协调 | 增加跨标签页互斥/通知和请求恢复标记，但服务端仍拒绝已消费 Token | 减少多个标签页或并发请求的竞争 | 不能恢复“服务端已提交、响应未交付”的情形，不能单独作为本缺陷修复 |
| C. 限时同操作幂等恢复 | 首次刷新携带随机操作 ID；在短暂窗口内，只有同一旧 Cookie 与同一操作 ID 的重试才能取回同一个后继凭据，不再创建第二个后继 | 可恢复网络中断、整页跳转和响应丢失 | 对“相同旧 Token + 相同操作 ID”开放有限重放；需持久化幂等关联，并能安全重建或解封后继 Token；需要跨标签页协调、清理和密钥轮换规则 |
| D. 无操作 ID 的宽限期 | 旧 Token 在短时间内重复返回其后继 | 服务端/客户端较简单 | 任何持有旧 Token 的请求都可在窗口内恢复后继，重放范围较大，不建议采用 |

## 建议的决策方式

- 如果“旧 Token 绝不重放”是不可改变的安全要求，选 **A**，接受轮换响应丢失时重新登录，并仅改善明确、可恢复的界面提示。
- 如果产品要求响应丢失后仍尽量保持登录，选 **C**，并明确接受“仅相同操作 ID 的短时幂等重试”这一有限例外。可将 30 秒作为待讨论的窗口起点，但必须由负责人确认后才能冻结。
- **B** 只能作为 **C** 的并发保护措施，不能替代服务端恢复语义。**D** 不建议。

## 若选择 C，实施前必须冻结的规则

1. 操作 ID 的生成、同标签页整页跳转期间的保存/清除，以及登出、换账号时的清理。
2. 操作 ID 与旧会话的一对一关联、有效时长、过期后的清理，以及不同操作 ID 并发时的失败语义。
3. 如何在仅存 Token 哈希的前提下重发同一个后继 Token：使用具备版本化密钥管理的确定性派生，或使用服务端密钥保护的短期密文；不能直接增加明文 Token 存储。
4. 多 API 实例、服务重启和密钥轮换期间如何恢复；账号版本变化、旧 Token 不匹配、数据库故障时仍须明确失败。
5. 真实 PostgreSQL/HTTP/浏览器验收至少覆盖：提交后丢响应并用同 ID 恢复、同 ID 并发只产生一个后继、不同 ID 重试被拒、账号状态/版本变化后恢复失败、过期恢复记录不可用、日志不含凭据。
