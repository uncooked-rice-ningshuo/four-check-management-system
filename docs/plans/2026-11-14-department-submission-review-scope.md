# 日常检查提交批次的审核归属调整方案

> 状态：本地服务端已修改，目标环境尚未加载或验收。依据 2026-11-14 对话确认的部门审核归属。当前分支 `feat-0.1-3`；目标环境未重新探测。

## 目标规则

1. 普通业务账号（委员、部长、副部长）提交记录时，批次归属账号主部门；页面只读展示该部门，服务端拒绝改选其他部门或管理员通道。目标部门还必须启用对应检查类型的录入映射。部长、副部长提交本人记录也遵循同一规则。
2. 普通部门批次只允许**批次所属部门**的部长、副部长在该类型的有效 `INSPECTION_REVIEW` 授权内确认或退回。仅因另一部门也负责相同检查类型，不得获得该批次审核权。现有流程允许具备审核权的提交人自审，继续保留。
3. `ADMIN` 可以把本人符合条件的管理员草稿提交到负责该类型且允许录入的部门，或提交到独立管理员通道；仍需有效录入、提交权限。目标部门批次由该部门负责人或有明确审核授权的管理员审核。独立管理员通道由有明确审核授权的管理员或超级管理员审核，不落入部门负责人队列。超级管理员保留全局审核能力。
4. 部门批次、管理员独立批次和历史校级批次保持不同归属；退回与重提沿用原批次去向，修订、审计和已冻结通报版本不回写。
5. 普通部门账号的批次列表、详情和待办只限账号主部门；另一部门即使负责同一检查类型，也不能读取该部门已提交的批次或历史修订。具有相应授权的管理员按授权范围查看、审核批次；超级管理员可查看全部。管理员仅有提交权时仍可查看本人提交的批次，用于跟踪结果及处理退回，不因此获得审核权。管理员独立通道不进入普通部门账号的批次列表。
6. 学生会办公室账号没有对应的有效 `INSPECTION_VIEW` 时不能查看检查提交批次；具备该权限时，沿用其现有的**仅已确认来源**读取规则，按授权检查类型及周期读取批次。查看授权不授予日常检查审核或其他写操作。

## 当前实现与差距

- `workflow.Service.Submit` 已用可信的 `PrimaryDepartmentID` 固定 `MEMBER` 的批次部门；`ADMIN` 可选择负责部门或独立通道。存储层重新检查部门与检查类型的录入映射、记录资格、版本和状态。共用提交组件在普通成员界面固定部门。
- `permission.Service.Effective` 将主部门映射的审核权生成为**仅按检查类型**限定的 `INSPECTION_REVIEW`。`DecideDepartmentBatch` 对批次记录使用该权限的 SQL 条件，因此两个部门映射同一类型时，双方负责人可交叉审核；零记录回执也有同样问题。
- 批次列表和详情由查看、记录管理或审核权限的并集控制。具备相同类型查看权的账号仍可能读取其他部门的批次；这与新的部门隔离规则冲突。原有技术方案明确映射检查动作按类型跨部门生效，本方案是对**提交批次读取与审核**的后续确认例外，实施时同步修订技术方案和原 11 月 10 日提交方案，不能只改一处 SQL。普通检查记录本身的跨部门查看范围不在此次批次规则中顺带改变。

## 实施设计

1. **服务端审核主体**：在工作流的审核命令中携带从认证/有效权限服务取得的系统角色、主部门和组织职务，不接受请求体提供这些值。普通部门负责人的审核判定同时要求 `MINISTER`/`VICE_MINISTER`、`batch.department_id = actor.primary_department_id`、该检查类型映射的审核权有效，并满足学年/学期/周次/类型的个人拒绝规则。`ADMIN` 使用单独有效的 `INSPECTION_REVIEW` 授权；`SUPER_ADMIN` 沿用全局授权。办公室日常检查写操作禁令继续有效。
2. **一次事务内检查**：审核前锁定批次并读取其归属与类型，再按主体类型校验；有记录批次与零记录回执共用批次级审核判断，随后沿用现有逐记录授权、状态、版本、锁定和审计校验。直接调用确认/退回 API 也必须拒绝越权，失败不得改动任何记录或批次。错误沿用稳定的 `FORBIDDEN_SCOPE` / 409 冲突语义。
3. **列表与详情**：服务端在批次列表与详情 SQL 上统一按批次归属过滤，历史修订随详情受同一限制。普通业务部门账号只读取 `batch.department_id = actor.primary_department_id` 的批次，并在该范围内继续检查对应检查类型和有效权限；不再用相同类型的查看、管理或审核权读取别的部门批次。学生会办公室只凭对应有效查看权读取已确认批次，未授权时列表为空、详情不可读。管理员按明确授权读取相应批次，只有提交权的管理员可读取本人已提交批次以处理退回；超级管理员可读取全部。管理员独立通道不进入普通业务部门账号列表。工作台部门状态只汇集普通账号主部门，避免泄露别部门批次数。直接请求无权读取的批次详情应返回不泄露批次是否存在的 404。页面继续使用既有操作入口，批次动作由服务端按批次归属和有效权限最终判定；不为本次改动新增响应字段或页面流程。
4. **提交界面**：普通业务账号展示固定主部门且不提供可更改选择；管理员的负责部门候选仅列可提交的映射部门，并保留独立管理员通道。提交前和事务中都按可信主体及实际记录复核。复用八类页面的共用提交组件，避免每页重复权限判断。
5. **文档与兼容**：同步 PRD、技术方案、11 月 10 日提交方案及项目状态中有关“审核按类型跨部门”“管理员通道审核”的当前口径。只改变未来审核授权判断；既有批次归属字段足够，无需回写历史数据或新增迁移。若实现中发现旧批次归属不可辨识，先盘点再决定是否需要只追加迁移。

## 验收矩阵与完成条件

在一次性 PostgreSQL 中建立部门 A/B 都映射同一检查类型的虚构账号和批次，覆盖实际记录与零记录回执：

| 操作者 | A 部门批次 | B 部门批次 | 管理员独立批次 |
| --- | --- | --- | --- |
| A 委员 | 可查看、提交本人合格记录，不可审核 | 不可查看、提交或审核 | 不可查看、提交或审核 |
| A 部长/副部长（有审核映射） | 可查看、审核；本人提交可自审 | 不可查看或审核 | 不可查看或审核 |
| B 部长/副部长（有审核映射） | 不可查看或审核 | 可查看、审核 | 不可查看或审核 |
| 仅有提交权的管理员 | 可按授权提交、查看本人批次，不可审核 | 可按授权提交、查看本人批次，不可审核 | 可按授权提交、查看本人批次，不可审核 |
| 获明确审核授权的管理员 | 按授权查看、审核 | 按授权查看、审核 | 按授权查看、审核 |
| 超级管理员 | 可查看、审核 | 可查看、审核 | 可查看、审核 |

- PostgreSQL/API 回归断言他部门批次不出现在列表和待办、直接请求详情返回 404、直接确认和退回拒绝且数据不变；覆盖同类型跨部门、撤权、账号换部门、零回执、退回重提、旧版本冲突、审计失败回滚及并发审核。
- 前端共用组件测试覆盖固定部门、管理员候选、仅本部门批次、管理员本人批次和审核操作；隔离真实 API/浏览器在两部门同类型场景走完提交、列表/详情跨部门不可见、本部门确认和管理员独立通道审核，检查八类页面复用入口及窄屏操作。
- 运行聚焦 Go/前端测试后，按跨端权限变更门禁运行后端 `gofmt`、`go vet ./...`、`go test ./...`，前端 `pnpm lint`、`pnpm test`、`pnpm build`；检查 Node/pnpm 与锁文件后再运行前端命令。真实环境版本加载与角色验收另行记录，不以本地通过代替。
