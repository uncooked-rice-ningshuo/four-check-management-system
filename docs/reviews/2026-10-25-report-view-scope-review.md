- **结论**：未发现可证实的越权或范围匹配错误。本次是窄范围静态审查，不是全仓库安全审计。

## 权限契约

项目权限规则要求：有效 ALLOW 共同提供可访问范围，匹配的单独 DENY 从中扣除，再与时间、检查类型、组织和数据维度相交。通报查询应在 SQL 聚合前应用数据范围。技术方案另明确超级管理员是全局绕过者；`REPORT_FORCE_GENERATE` 是独立例外，超级管理员身份不会自动授予该动作。

## 参与方与证据

1. **身份 → 有效权限**：`server/internal/reporting/service.go` 每次请求调用权限服务并只收集 `REPORT_VIEW` 规则。无不带 class/grade 限制的 ALLOW 时服务端拒绝；权限服务为每个请求实时读取角色、主部门、部门检查类型映射和用户单独规则。超级管理员得到全局 `REPORT_VIEW` ALLOW；该行为符合技术方案的全局绕过约定。办公室负责人默认权限与其他用户的指定授权均通过相同的 Repository 过滤路径。
2. **有效权限 → 周期列表**：`ListReportPeriods` 先构造部门检查范围与已有提交候选，再通过 `reportPermissionPredicate` 在 `EXISTS` 查询中检查当前候选的年/学期/周/类型/部门。授权只覆盖部门的用户看不到只含校级批次的周期；宽范围用户可以看到它。
3. **有效权限 → 部门汇总**：`ReportSummary` 为每个部门/检查类型单元按五个可查询维度编译 allow 谓词，并从命中 allow 的单元中减去 deny；查询在数据库侧过滤后才读取批次计数和记录数组，没有先加载全量再在内存过滤。
4. **部门范围 → 校级行**：校级行使用 `department_id IS NULL` 的独立批次，并单独编译范围谓词。无部门限制的授权可访问校级单元；具体部门 ALLOW 不会授权校级行，具体部门 DENY 也不会误删独立校级行。PostgreSQL 仓储测试明确覆盖了这两种方向。
5. **class/grade 限制**：产品允许 `REPORT_VIEW` 的 class/grade DENY，但聚合行没有班级/年级拆分。实现把此类 deny 在其他维度匹配时作为保守限制处理；单独 class/grade ALLOW 不授权部门级聚合，且权限校验会拒绝创建此类 allow。该实现避免把局部数据读取能力扩成整个部门汇总权限。
6. **输入和 SQL 边界**：期间 ID 在服务层规范化并校验 UUID；谓词使用参数占位符。列名由代码固定，不由请求提供。无可见汇总行不会被转成成功空汇总，而是返回稳定拒绝结果。

## 反驳与结果

- **候选：部门范围 DENY 应隐藏校级汇总。** 已有 PostgreSQL 测试验证具体部门 deny 隐藏部门行但保留校级独立行。校级不是该部门的数据，拒绝不应扩大到互不隶属的记录。
- **候选：任一 ALLOW 已足够，即使存在匹配 DENY。** SQL 将所有匹配 DENY 作为整体排除条件，与权限服务单独拒绝优先语义一致。
- **候选：Class/grade deny 可能过宽。** 汇总不包含这两个维度，无法计算一个部门单元扣除局部数据后的安全总值；当前策略只会隐藏更大范围的匹配单元，不会暴露 DENY 范围内的数据。与其扩大访问相比，这属于保守结果，且代码注释已说明该行为。
- **结论**：以上候选均未形成支持越权/错误结果的可达执行；本次没有安全或正确性发现。
