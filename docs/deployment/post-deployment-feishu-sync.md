# 部署成功后的飞书功能说明同步流程

本流程适用于本系统每一次服务器部署或版本更新。用户已授权：部署成功后，无需再次询问，按本文件更新指定飞书 Wiki，并向指定群发送《功能更新说明》。该授权只覆盖下列文档和群聊。

## 固定目标与身份

- **Wiki**：[发布更新记录](https://acna9bso0eml.feishu.cn/wiki/UrU3wf8uPiW9ZzkK89gcal99n4c?from=from_copylink)。每次部署在文档末尾追加带日期和版本号的新小节，保留历史记录。
- **群聊**：“日常管理系统 leader”，群 ID `oc_cb0934e9c7dd0f5c9741ab43595266b3`。发送前核对群名和 ID，避免同名群发错。
- **工具与身份**：使用宁硕的飞书 CLI（`lark-cli`）。按当前已验证的权限方式编辑 Wiki（`--as user`）；群公告以应用机器人身份（`--as bot`，宁硕的飞书 CLI）发送。

## 执行时机与成功门槛

仅在目标服务器部署完成并通过技术核验后发布成功说明。至少确认：

1. 目标环境运行的是本次预期的 API/Web 版本或镜像标签。
2. 本次要求的数据库迁移已应用，迁移账本与发布包预期一致；没有数据库变更时记录“无迁移”。
3. 必需容器/服务处于预期健康状态，应用就绪检查成功。
4. 与本次改动相关的必要冒烟检查通过，并记录未覆盖的业务或角色验收。

若部署或关键技术检查失败，不发送“部署成功”公告；先在项目部署日志记录失败现象、当前版本和恢复状态。修复后重新核验，通过后再进入本流程。技术部署通过但部分业务/角色验收尚未完成时，仍按时同步，但必须把这些项目明确列为“待验收”，不能写成已完成。

## 固定步骤

1. **整理本次事实**：从实际部署回执、迁移账本和验证结果中确认环境、日期、版本、迁移、用户可见功能、修复内容、验证结果和剩余验收项。更新包说明可作参考，不能把未部署的本地改动写成已上线功能。
2. **先记项目部署日志**：在对应部署记录中补充部署结果、实际镜像/版本、迁移状态、服务与就绪检查、业务验收边界，以及本次飞书同步链接或消息 ID。不得记录密码、Token、Cookie、数据库凭证、学生个人信息或其他敏感数据。
3. **更新 Wiki**：在固定 Wiki 末尾追加 `YYYY-MM-DD｜<版本> 功能更新与部署记录` 小节，按“部署版本与迁移、功能变化、技术核验、待验收/已知限制”记录。写入后重新读取页面，确认新小节存在、内容完整且没有覆盖旧记录。
4. **发送群说明**：向固定群发送标题为 `【功能更新说明｜<环境>｜<版本>】` 的消息。摘要应简洁，列出用户可感知的更新、部署核验结果、尚未完成的验收，并附 Wiki 链接。以 `--as bot` 使用宁硕的飞书 CLI 应用机器人身份发送。
5. **核实并收尾**：确认 Wiki 回读成功、群消息发送成功且目标群正确；把 Wiki 链接、发送时间和消息 ID（若 CLI 返回）记入部署日志。两项都成功后，本次同步才算完成。

## 群消息模板

```text
【功能更新说明｜<测试/正式环境>｜<版本/日期>】
部署结果：API/Web <版本>；数据库迁移 <范围或“无迁移”>。

本次更新：
1. <已部署的功能或修复及用户影响>
2. <已部署的功能或修复及用户影响>

部署核验：<容器/服务健康、就绪检查及关键冒烟结果>。
待验收/已知限制：<列明未完成项；没有则写“无”>。
详情：<飞书 Wiki 链接>
```

没有用户可见功能变化时，仍发送部署说明，并明确写“本次无用户可见功能变化”，简述部署维护内容和核验结果。不要把 HTTP 就绪检查等同于全部业务验收通过。

## 失败重试与完成定义

- Wiki 已更新但群消息发送失败：只重试群消息；群消息已成功但 Wiki 写入失败：只补写 Wiki。不要因为飞书同步失败而重跑已成功的部署或数据库迁移。
- 重试发送前先检查目标群最近消息，避免重复公告；每次部署使用唯一、可追溯的消息幂等键（建议由项目名、版本和日期组成），并记录 CLI 返回的消息 ID。
- 若目标页面或群身份无法核实、CLI 权限不足或内容与实际部署状态不一致，暂停对应外部写入，在项目日志记录阻塞点；不要改发到相似页面或群聊。
- **完成条件**：部署事实已记入项目日志；指定 Wiki 已追加并回读确认；指定群已收到功能说明；待验收边界已明确记录。
