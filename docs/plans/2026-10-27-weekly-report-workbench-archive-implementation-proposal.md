# 通报工作台与通报归档实施方案

- 日期：2026-10-27
- 状态：用户已确认方案并要求实现；PRD、技术方案、页面梳理、代码和验证状态按本文件及项目状态同步。
- 范围：周通报工作台、草稿数据版本、定稿数据、通报归档，以及 Word/Excel 输出控件的页面预留。本文不包含 HTML 原型，也不实现模板、文件生成、存储和下载逻辑。

## 1. 方案结论

### 1.1 页面结构

通报管理收敛为两个页面：

1. **通报工作台**：在同一个页面中按顺序完成“确认来源数据 → 编制和修订草稿数据 → 确认定稿数据”。
2. **通报归档**：只列出已经成功生成过至少一个草稿版本的周通报；可查看各周当前状态、版本及数据快照。

工作台不再另设“数据汇总与统计”“草稿”“审核”“定稿导出”“更正版本”等重复页面。汇总和来源核对进入工作台第一步；草稿编辑、审核和定稿动作留在对应阶段内；更正从归档发起，仍回到同一工作台编制新版本。

### 1.2 “生成”的含义

- **生成草稿**：根据当时已确认的来源数据，创建一个平台内的草稿数据集版本。
- **生成定稿**：确认当前草稿数据集无误，将其固定为不可原位修改的定稿数据快照。
- **生成 Word/Excel**：独立于数据状态的输出能力，草稿阶段基于当前草稿版本生成草稿文件，定稿阶段基于已确认定稿版本生成定稿文件。通报工作台和通报归档都预留相应控件；归档中的操作必须针对用户明确选中的版本。具体模板、文件生成、存储和下载功能后续实现，不作为草稿保存、提交审核或定稿的前置条件，也不改变数据版本状态。

### 1.3 历史更正

定稿数据不原位修改。用户从归档中选择“基于当前有效定稿创建更正版本”，系统保留原定稿，以原定稿数据为基础建立新的草稿版本；完成同一套草稿编制和定稿步骤后，新版本成为当前有效定稿。

## 2. 实施结果与当前边界

实施沿用原分支和工作区已有通报改动，保留其他未提交文件；没有创建分支/工作树，也未部署或修改目标数据库。

| 能力 | 当前实现/边界 |
| --- | --- |
| 页面 | 工作台分三阶段；归档只读展示 currentVersion > 0 的周次。旧路由重定向到工作台。 |
| 交互布局 | 周期选择位于标题右上；刷新位于汇总表右上；来源表取消外层卡片和 KPI 卡；工作流区域压平；阶段操作栏固定在视口底部。 |
| 版本明细 | 草稿和定稿均按部门/检查类型分类，每类可打开对应不可变版本的分页明细。草稿支持字段修正、从本版排除/恢复纳入；事实变化需部门重确认。 |
| 定稿 | 定稿确认只固定结构化数据；Word/Excel 模板、文件生成、存储和下载后续实现，不作为定稿门槛。 |
| 输出预留 | 工作台草稿/定稿和归档所选版本均显示 Word/Excel 控件；当前禁用并说明后续开放。 |

当前相关实现主要包括：

- 前端：WeeklyReportSummaryPage（工作台）、WeeklyReportWorkflowPanel、WeeklyReportArchivePage；旧草稿页面不再单独挂路由。
- 后端：周通报摘要、草稿生成、状态转换、修正、工作流读取和归档读取接口。
- 数据库迁移：031–034 定义周报、不可变版本、来源记录快照、审核/修正记录、零记录回执快照及本版纳入/排除调整；未应用到目标运行库。
- 现有报告版本保存确认记录数量与明细导航快照，不包含 Word/Excel 版式内容。

## 3. 信息架构和导航

### 3.1 导航

| 导航项 | 页面职责 | 主要权限 |
| --- | --- | --- |
| 通报工作台 | 创建/继续当前或有权访问周次的通报；完成数据核对、草稿编制、最终确认 | REPORT_VIEW、REPORT_GENERATE、REPORT_CORRECT、REPORT_REVIEW、REPORT_RETURN、REPORT_FINALIZE 等按动作独立校验 |
| 通报归档 | 查询所有已生成至少一个草稿版本的周通报，查看只读历史和版本轨迹 | 独立 ARCHIVE_VIEW，按报告完整数据范围过滤 |

现有工作台首页摘要可继续作为第一步的数据来源。现有“数据汇总与统计”不再作为通报流程的独立导航入口；原 URL 可在过渡期重定向到工作台第一步，避免旧书签失效。

`REPORT_VIEW` 只覆盖报告部分部门/类型时，第一阶段仍显示经服务端过滤的授权汇总。若报告版本内含超出该账号范围的单元，完整草稿/定稿快照继续由后端拒绝；工作台保留周期与授权汇总，停留在来源核对阶段并说明权限边界，不向前端暴露越权版本数据。

### 3.2 周次选择

- 默认使用系统工作上下文中的当前周，并确认该周属于用户可查看范围。
- 用户没有当前周或当前周无权查看时，保持未选择并说明原因；不得默认选中周期列表第一项。
- 如有权处理其他周期，允许明确选择周期。归档创建更正时，将归档中的学期/周次带入工作台，不重新猜测周期。
- 每学期、每周最多一个逻辑报告；同一周的重生成和更正通过递增版本完成。
- 页面标题行右上角放置周期选择器；已选周期的日期范围与选择器同组显示。

## 4. 三阶段交互

### 阶段一：确认来源数据

**目的：** 判断本周应交数据是否完整，并确认草稿将引用哪些已确认记录。

**页面内容**

1. 页面标题行右上角提供周期选择器和所选周期起止日期。
2. 汇总表标题行展示行内汇总数字；刷新、展开/收起操作放在右侧。表格不套 KPI 卡或外层内容卡。
3. 部门 / 检查类型表格：
   - 部门或校级范围；
   - 检查类型、是否为本周应交项；
   - 提交批次数、待审核数、退回数、已确认批次数；
   - 已确认记录数、已确认零记录回执数；
   - 完成状态、来源明细入口。
4. 单元详情抽屉：提交批次、确认修订号、确认时间、记录数、授权范围内的记录明细。

**操作**

- 刷新来源摘要。
- 查看来源记录和零记录回执。
- 数据完整时，执行“基于已确认数据生成草稿”。
- 阶段主要操作固定在浏览器视口底部，页面内容区预留底部空间。
- 存在未完成应交项时，默认阻止生成并列出部门/类型；符合现行独立权限的负责人可走强制生成流程，填写理由并记入审计。强制生成不把未确认数据伪装成已确认或零条。

**数据口径**

- 只把部门已确认记录纳入默认草稿。
- 零记录回执只表示该应交单元完成，不计入业务记录数。
- 未接入、无批次或没有记录，不等于已完成且零条。
- 首期只展示已确认记录数及可追溯明细；不增加比率、处分风险或未批准的派生指标。
- 周期、部门与检查类型关系来自应交配置和授权，不写死部门/类型映射。

### 阶段二：编制和修订草稿数据

**目的：** 核对本版数据集，并对“本次通报包含哪些数据”进行留痕调整。这里呈现结构化数据，不呈现 Word/Excel 文档版式；本阶段预留“生成草稿 Word”“生成草稿 Excel”控件，后续基于当前草稿版本生成输出。

**页面内容**

- 当前版本号、版本状态、生成时间、生成者、引用的来源修订。
- 纳入记录数、数据单元数、零记录回执数、本版调整项数、待部门重确认数。
- 按部门 / 检查类型分组的数据集列表；可展开到记录明细。
- 每行展示纳入状态、来源批次/修订、记录摘要、记录数及本版状态。
- 版本轨迹及调整记录：旧版本、新版本、操作者、时间、原因、前后值。

**支持的调整**

1. **更正字段**：在通报版本中保存修正前值、修正后值、原因、操作者、时间及来源记录关联；不直接覆盖部门原始提交修订。
2. **排除本版数据**：表示该记录不进入当前报告版本，绝不删除来源业务记录。
3. **补充数据**：只能从用户有权查看且已确认的来源记录中补入；不能在通报草稿中凭空新造未经确认的业务事实。
4. **事实变化**：标记为需要来源部门重新确认；未确认前阻止该事实进入可定稿版本。部门重确认后，刷新来源并生成新的草稿版本。

**版本规则**

- 初次生成创建 V1；之后对数据集的每次显式保存都创建 V(n+1)，不原位更新已生成版本。未保存的表单改动只在当前编辑会话中保留。
- 每次修正、排除或恢复纳入都直接生成新版本。“读取最新来源并生成新版本”会重新核对已确认来源并吸收后来确认的数据；操作前通过确认窗口说明手工修正和排除项不会沿用，用户确认后再生成，旧版本和调整审计持续保留。
- 新来源批次、来源确认修订或零回执修订与本版来源指纹不一致时，显示“来源已变化”，阻止将陈旧草稿直接提交定稿；用户刷新并生成新版本。
- 对并发编辑携带 rowVersion；版本过期返回 409/VERSION_CONFLICT，保留用户输入并提示刷新，不静默覆盖。
- 业务“删除”在页面上表达为“从本版排除”，而非物理删除数据。

**阶段操作**

- 保存修订并生成下一草稿版本。
- 从最新确认数据重新生成新草稿版本，并在生成前核对数据差异。
- 预留“生成草稿 Word”“生成草稿 Excel”控件，明确输出基于当前选中的草稿版本；当前方案阶段不实现文件生成能力，控件应标注“后续开放”并保持不可触发，不能表现为已生成或下载成功。
- “草稿数据核对无误，提交定稿确认”进入阶段三。
- 退回修订后回到此阶段；退回原因和版本轨迹可查。

### 阶段三：确认定稿数据

**目的：** 对将进入历史定稿库的确切数据集做最后确认。

**页面内容**

- 学年 / 学期 / 周次、草稿版本、来源指纹、确认记录总数。
- 按部门 / 检查类型的记录数、纳入明细、零记录回执和范围受限提示。
- 未完成应交项、来源已变化项、待部门重确认项、草稿调整轨迹。
- 确认人、审核人、生成时间及操作说明。
- 定稿确认后预留“生成定稿 Word”“生成定稿 Excel”控件，基于本次已确认的定稿版本生成输出；定稿前不提供可误认为定稿文件的操作。

**审核与定稿动作**

- 保留现行审核、退回和定稿权限的独立服务端检查，但把审核动作放在本阶段，不创建独立审核页面。
- 审核未通过时填写原因并退回阶段二。
- 审核通过后，有 REPORT_FINALIZE 权限的用户执行“确认并生成定稿数据”。如同一用户具备两种权限，可在同一阶段依次完成审核和定稿；不强制创建者与审核人分离。
- 定稿成功后固化结构化数据集、来源记录版本、确认修订号、回执、统计口径版本和操作轨迹。定稿数据不可原位修改。
- **定稿不检查 Word/Excel 文件或模板。** 文件生成失败、模板未配置、尚未选择输出格式，均不影响定稿数据状态。定稿确认后，工作台可从该阶段生成定稿输出；生成状态与定稿状态分开记录。

## 5. 状态与版本规则

### 5.1 用户可见的三阶段

| 阶段 | 主要状态 | 用户可执行动作 |
| --- | --- | --- |
| 确认来源数据 | 尚未生成草稿 / 来源待补齐 / 可生成 | 查看批次、回执、明细；生成草稿；具备单独权限时强制生成 |
| 编制和修订草稿 | 草稿编辑中 / 草稿已退回 / 来源已变化 / 待来源部门重确认 | 修改本版、排除或补入已确认记录、生成新版本、提交定稿确认 |
| 确认定稿数据 | 待审核 / 审核通过待定稿 / 已定稿 | 审核、退回、确认并定稿 |

### 5.2 后端状态兼容建议

现有状态包括 DRAFT、PENDING_REVIEW、RETURNED、FINALIZING、FINALIZED、PUBLISHED、ARCHIVED。建议：

- 保留 DRAFT → PENDING_REVIEW → FINALIZING → FINALIZED 的服务端权限和审计边界；界面把审核和定稿操作合并显示在第三阶段。
- 将 FINALIZING 的用户文案从“等待定稿文件”改为“审核通过，待定稿确认”。状态转换不再等待文件元数据；若后续统一状态名，使用只追加迁移和兼容映射，不重写已应用迁移。
- 退回保持 RETURNED，返回第二阶段。重生成仍追加新版本。
- PUBLISHED / ARCHIVED 仅表示后续发布或行政归档状态；本方案不设计发布渠道，也不将发布等同于数据定稿。
- 历史定稿需要修改时，基于当前有效定稿建立新的更正草稿版本；旧定稿仍可查询。

## 6. 通报归档

### 6.1 列表范围

只返回已成功生成草稿的报告：

~~~sql
weekly_reports.current_version >= 1
~~~

仅有摘要数据、从未生成草稿、或尚无版本的周次不出现在归档列表。已生成草稿但仍处于草稿、待审核、已退回、待定稿、已定稿、已发布或已归档状态的周次均可按权限显示。

### 6.2 列表字段与操作

| 字段 | 说明 |
| --- | --- |
| 学年 / 学期 / 周次 | 以报告快照周期为准 |
| 当前状态 | 草稿、待审核、已退回、审核通过待定稿、已定稿、已发布、已归档 |
| 当前有效版本 / 总版本数 | 展示目前工作版本和可追溯版本数量 |
| 当前版本已确认记录数 | 不包含零记录回执 |
| 数据单元数 / 零记录回执数 | 展示来源覆盖情况 |
| 生成 / 更新 / 定稿时间 | 按当前版本事件展示 |
| 权限范围标识 | 标识局部范围，不暗示为全院完整数据 |
| 操作 | 查看快照；活动草稿可“在工作台继续”；已定稿报告可“创建更正版本” |

归档详情针对明确选中的报告版本预留输出操作：草稿版本显示“生成草稿 Word / Excel”，定稿版本显示“生成定稿 Word / Excel”。当前仅预留控件位置和版本上下文；后续实现生成逻辑。不得从列表行直接生成而未说明版本，也不得把归档详情中的输出操作设计成修改历史数据。

支持学年、学期、周次、状态筛选、分页和刷新。归档列表与详情均只读；所有修订和最终确认回到工作台完成。

### 6.3 详情抽屉

- 当前有效状态及版本。
- 各版本的创建时间、操作者、引用来源、记录数、回执数和范围标识。
- 每版本按授权范围展开数据明细。
- 审核/退回/定稿时间线。
- 通报内修正、事实变化及来源部门重确认决定。
- 原定稿与更正定稿并列可追溯；不得用最新值覆盖历史快照。
- 当前选中版本对应的 Word/Excel 输出控件；仅对已有相应数据状态的版本展示，未来生成结果关联该版本，不覆盖旧输出记录。

## 7. 数据模型与字段方案

以下区分“已有字段可复用”和“需要确认或补充的字段”。字段名使用现有 API 的 camelCase 约定；数据库仍使用 snake_case。

### 7.1 报告周期与汇总单元

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| academicYearId, academicYearName | ID / string | 学年 |
| semesterId, semesterName | ID / string | 学期 |
| weekId, weekNo, startDate, endDate | ID / int / date | 周次和日期范围 |
| departmentId, departmentName | ID / string | 部门范围；校级行使用显式 collegeLevel |
| collegeLevel | boolean | 区分校级汇总，不以空部门 ID 推断 |
| inspectionTypeId, inspectionTypeName | ID / string | 检查类型，来源于配置 |
| isRequired | boolean | 本周应交配置 |
| submissionCount, draftBatchCount, pendingReviewBatchCount, returnedBatchCount, confirmedBatchCount | int | 来源提交和审核状态 |
| confirmedRecordCount | int | 已确认业务记录数；不含零回执 |
| zeroRecordPendingReviewBatchCount, zeroRecordReturnedBatchCount, zeroRecordConfirmedBatchCount | int | 零回执单独统计 |

### 7.2 报告主记录与版本

现有主记录/版本模型继续复用：

| 字段 | 所属 | 用途 |
| --- | --- | --- |
| id, semesterId, weekId | weekly_reports | 同一学期周次唯一逻辑报告 |
| status, currentVersion, rowVersion | weekly_reports | 当前状态、当前版本、乐观锁 |
| createdBy, createdAt, updatedBy, updatedAt | weekly_reports | 主记录审计元数据 |
| finalizedBy, finalizedAt | weekly_reports | 当前定稿操作者和时间 |
| id, reportId, versionNo | weekly_report_versions | 不可变版本标识 |
| contentJson | weekly_report_versions | 周期、汇总行、确认记录数、未完成单元、重确认状态、统计规则版本、范围受限标记、生成时间 |
| sourceFingerprint | weekly_report_versions | 防止源数据变化后误用旧版本 |
| forcedGenerationReason | weekly_report_versions | 强制生成理由 |
| createdBy, createdAt | weekly_report_versions | 版本生成者和时间 |

每个版本的来源记录继续以 weekly_report_version_records 保存：

- reportVersionId
- inspectionRecordId
- sourceSubmissionId
- sourceRevisionNo
- recordVersion
- includedDataJson：经过报告字段白名单投影的不可变显示快照

零记录回执继续使用 weekly_report_version_zero_receipts 记录来源提交 ID 与确认修订号。

### 7.3 版本内数据字段

现有通报记录投影可继续使用类型化字段：

- 通用：id、typeCode、studentName、studentNumber、className、grade。
- 时间/业务细节：details.date、details.time、details.period、details.round、details.absenceHours、details.absenceCount、details.result、details.reasonCode、details.description、details.remark。
- 关联显示名称：currentDormitoryName、currentCourseName、currentClassroomName、currentAreaName、currentReasonLabel。
- 责任对象：responsibleClasses、responsibleStudents、responsibleDormitories。

明细字段按检查类型白名单投影；不得把完整原始 JSON 直接返回给页面。学号、姓名等个人信息仅在当前权限范围内最小化展示和导出；列表聚合不包含个人敏感字段。

### 7.4 草稿调整与修正审计

现有 weekly_report_corrections 继续承担字段更正，保存：

- reportId、reportVersionId、inspectionRecordId；
- field、beforeJson、afterJson；
- reason、factChanged、departmentReconfirmationStatus；
- correctedBy、correctedAt；
- 部门决定：decision、decisionComment、decisionActorId、decisionCreatedAt；
- 事实变化时关联 sourceSubmissionId，部门确认结果不得覆盖原提交修订。

本版“纳入 / 排除 / 补入”属于版本范围调整，不是业务字段更正。实施前先验证现有版本快照是否足以表达并审计这三种操作；如不足，新增只追加的 weekly_report_version_adjustments，建议字段为：

- id、reportId、reportVersionId、sourceRecordId、sourceSubmissionId、sourceRevisionNo；
- operation（INCLUDE / EXCLUDE）、beforeIncluded、afterIncluded；
- reason、actorId、createdAt。

不得用物理删除实现排除；补入的数据必须关联已确认来源记录。任何新表均需追加迁移、唯一/外键约束、审计和并发校验。

### 7.5 归档响应

扩展现有 ReportArchiveEntry，避免仅返回定稿报告：

- id
- period
- status
- versionNo、versionCount
- confirmedRecordCount、cellCount、confirmedZeroReceiptCount
- scopeLimited
- createdAt、updatedAt
- 可选 finalizedAt、publishedAt

查询条件必须以 currentVersion >= 1 为基础，再应用显式状态筛选、分页和 ARCHIVE_VIEW 数据范围。总数与列表使用同一授权过滤条件。

### 7.6 Word/Excel 输出记录（后续功能的数据设计预留）

文件输出是与报告数据版本关联的独立产物。草稿和定稿分别生成，不能只挂在报告主记录上，否则无法区分同一周的多个版本及其输出阶段。后续实现时可采用单独的输出任务/产物记录，建议字段如下；本方案阶段只预留页面控件，不新增表、API 或实际文件处理代码：

| 字段 | 用途 |
| --- | --- |
| id、reportId、reportVersionId | 输出产物及其所属报告、确切数据版本 |
| stage（DRAFT / FINAL） | 标明草稿输出或定稿输出 |
| format（DOCX / XLSX） | 输出格式 |
| templateVersionId | 使用的模板版本；无模板时不得伪称模板化输出 |
| status（QUEUED / GENERATING / READY / FAILED） | 输出任务状态，独立于报告阶段状态 |
| objectKey、checksum、fileSize | 服务端文件定位和完整性字段，不直接暴露存储 key |
| generatedBy、generatedAt、failureCode | 操作者、生成时间和可诊断的稳定失败码 |

重新生成应追加新的输出记录或任务版本，保留此前成功产物和失败审计。定稿输出必须引用不可变定稿版本；更正定稿生成的新输出与旧定稿输出并存。

## 8. API / 应用服务方案

尽量复用现有 API，主要改造读取范围、状态门槛和版本调整语义：

| API | 本方案用途 | 改造点 |
| --- | --- | --- |
| GET /reports/periods | 工作台周期选项 | 继续遵守工作周默认规则和授权过滤 |
| GET /reports/summary | 工作台阶段一汇总 | 保持只读，不加入草稿状态副作用 |
| GET /reports/records | 查看授权单元内来源明细 | 保持类型化白名单和分页 |
| GET /reports/workflow | 读取当前周报告、版本、审核和修正轨迹 | 覆盖阶段和版本状态读取 |
| POST /reports/drafts | 初次生成草稿，或基于已确认来源和经用户确认的调整生成新版本 | 记录幂等键/版本号、快照指纹、调整差异及强制生成理由 |
| POST /reports/:id/submit | 提交定稿确认 | 携带 rowVersion，进入阶段三 |
| POST /reports/:id/approve、/return | 阶段三审核和退回 | 追加审核记录；退回理由必填 |
| POST /reports/:id/finalize | 定稿数据确认 | 移除 Word/Excel 元数据存在性门槛；仍需校验来源指纹、重确认状态、权限和 rowVersion |
| POST /reports/:id/corrections、POST /report-corrections/:id/decision | 字段修正和部门重确认决定 | 保留前后值、原因及决定审计 |
| GET /reports/archive | 归档列表 | 从“仅最终状态”改为 currentVersion >= 1，新增状态筛选 |
| GET /reports/archive/:semesterId/:weekId | 归档详情 | 返回仅授权可见的版本、明细和轨迹 |
| 必要时新增版本范围调整 API | 纳入/排除/已确认记录补入 | 只作用于当前草稿版本并留痕 |

本方案不新增 Word/Excel 生成、查询或下载 API。后续实现时应提供以 `reportVersionId + stage + format` 为明确上下文的生成和产物读取能力，并单独校验生成、查看、下载权限；不能复用定稿接口承载文件副作用。

副作用操作必须服务端校验状态、操作者权限、报告范围、来源指纹和版本号，并使用幂等键或数据库唯一约束防止重复提交。前端的流程步骤和按钮禁用只用于引导，不作权限边界。

## 9. 权限、安全和审计边界

- REPORT_VIEW 控制工作台来源汇总和可见记录范围；REPORT_GENERATE 控制草稿生成；REPORT_CORRECT 控制通报内修正；REPORT_REVIEW、REPORT_RETURN、REPORT_FINALIZE 分别控制审核、退回、定稿。
- REPORT_FORCE_GENERATE 继续独立授权，不由超级管理员或一般通报查看权自动推导；强制生成须有理由和审计。
- Word/Excel 生成能力后续应有独立的服务端授权动作（名称待权限方案确认）；不得把页面预留按钮当作授权，也不得复用 REPORT_FINALIZE 或 ARCHIVE_VIEW 代替生成权限。
- ARCHIVE_VIEW 继续作为独立归档动作，不从 REPORT_VIEW 自动继承。需负责人确认它是否覆盖所有已生成草稿，包括未定稿版本；本方案建议覆盖，以符合“只显示生成过草稿的每周数据”。
- 对含有任何越权检查类型或部门数据的报告，不返回该报告的归档元数据或明细；页面显示范围受限标签，不将部分授权结果表述为全院完整通报。
- 定稿快照、来源记录关联、修正记录和状态事件追加写入；普通业务接口不得修改或删除历史快照。
- 后端列表、详情、导出（未来）分别执行授权；不得依赖按钮显隐或前端过滤。

## 10. 错误、空态和恢复

| 场景 | 页面反馈与动作 |
| --- | --- |
| 无当前周 / 当前周无权查看 | 工作台不自动选首周；显示原因和可用周期选择 |
| 无应交配置 | 区分“配置缺失”与“已完成零记录”，提示有权负责人补齐配置 |
| 存在未确认或退回单元 | 默认阻断生成，列明阻断单元；有强制权限者可填写理由继续 |
| 数据加载失败 | 与空数据明确区分；保留筛选并提供重试 |
| 来源指纹变化 | 标记草稿过期，阻止提交/定稿，允许基于最新确认数据生成新版本 |
| 部门重确认待处理 | 显示对应修正和来源部门，阻止使用未确认事实定稿 |
| 并发版本冲突 | 返回稳定 409/REPORT_VERSION_CONFLICT，刷新报告状态，保留用户输入 |
| 重复点击生成/定稿 | 幂等返回已有结果或返回明确冲突，不创建重复版本 |
| 输出控件尚未开放 | 显示“文件生成功能后续开放”，按钮不可触发，不展示虚构的文件状态或下载链接 |
| 后续文件生成失败 | 只将对应输出任务标记失败并允许重试；不改变草稿/定稿状态，不丢失结构化数据快照 |
| 无归档记录 | 显示“尚无生成过草稿的周通报”；不显示只做过汇总的周次 |
| 权限撤销 | 清理对应 Query 缓存并隐藏旧范围数据；403 不保留过期敏感数据 |

## 12. 验收标准

1. 通报管理导航只有“通报工作台”和“通报归档”两个入口；来源汇总属于工作台第一阶段。
2. 三阶段使用同一周次和报告上下文；不能跳过前置生成或未完成的数据门禁。
3. 草稿明确显示为结构化数据集；页面没有将 Word/Excel 版式或文件校验伪装成数据确认。
4. 每次显式生成新草稿版本都保存不可变来源快照；来源变化不会静默改写旧版本。
5. 草稿支持本版修正、补入和排除；排除不删除源记录，事实变化等待部门重新确认。
6. 定稿仅冻结数据并记录确认人/时间/版本/来源；没有文件或模板时仍可成功定稿。
7. 工作台在草稿阶段和定稿阶段均预留对应 Word/Excel 控件；归档详情也按明确选中的草稿或定稿版本预留控件；本轮控件不可触发，且不暗示已实现文件生成。
8. 定稿不可原位修改；历史更正创建新版本，原定稿仍可查看。
9. 归档只含 currentVersion >= 1 的周报告；仅有摘要、从未生成草稿的周次不可见。
10. 归档的列表、总数、版本和明细严格一致地按 ARCHIVE_VIEW 和全部版本范围授权过滤。
11. 加载失败、无数据、无权限、并发冲突、来源变化、待重确认和重复请求均有明确反馈和可恢复路径。
