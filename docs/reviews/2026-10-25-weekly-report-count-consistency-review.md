# 周通报汇总记录数一致性审查

## 审查范围

- **基线**：`feat-0.1-2`，HEAD `37c0413`，检查当前未提交工作区中的实现。
- **维度**：正确性。
- **范围**：检查记录提交 → 批次当前修订 → 确认状态 → 周汇总 SQL 的记录数来源，重点验证重复记录、退回重提、历史修订与并发提交是否会造成遗漏或重复计数。
- **结果**：没有发现普通应用路径下可达的错误计数执行。
- **改动**：本次只读审查，没有修改产品代码。

## 需要保持的契约

统计记录数时，一个检查记录只能属于一个部门/校级提交批次；同一批次中的记录 ID 不重复；一个批次只贡献其当前确认修订的记录数，历史修订不重复累加。退回重提必须沿用原批次与原记录集合，只递增修订号。

## 跨边界证据

1. **提交输入 → 数据库锁定**：`server/internal/workflow/model.go` 规范化记录 UUID、按 ID 排序并拒绝重复 ID。`server/internal/store/workflow.go` 的提交事务只接受周期、部门、检查类型完全匹配且状态为草稿、`submission_id IS NULL`、未锁定、未删除的记录；读取时 `FOR UPDATE` 并核对行版本，再将记录状态和唯一 `submission_id` 更新、保存首版 `record_ids` 与业务快照并写审计。所有效果在同一事务提交。
2. **提交关联 → 批次范围**：`server/migrations/016_department_submissions.sql` 对检查记录建立包含提交 ID、学期、周次、部门和检查类型的复合外键，避免记录关联到不匹配的批次。单条检查记录只有一个 `submission_id` 字段，普通 API 无法将同一行同时挂到两个批次。
3. **审核 → 当前记录集合**：审核流程从批次当前 `revision_no` 读取该版 `record_ids` 的数量，并查询同一 `submission_id`、当前状态且授权范围内的完整记录集合；数量不匹配时拒绝整笔事务。已有 PostgreSQL 并发用例确认同一记录并发提交只有一个批次成功，且并发重提只有一个新修订成功。
4. **退回重提 → 新修订**：重提服务再次规范化、排序并拒绝重复记录 ID；Repository 要求 ID 顺序与上一版数组完全一致，校验每条原记录当前仍属于该批次且状态、版本有效，再在同一事务更新状态、递增 `revision_no`、插入新快照。迁移 017 的触发器禁止更新或删除旧修订。
5. **当前修订 → 汇总 SQL**：`server/internal/store/reporting.go` 以 `rev.submission_id=ds.id AND rev.revision_no=ds.revision_no` 连接当前版本；确认记录数只对 `ds.status='CONFIRMED'` 求该版 `record_ids` 数量。它不会遍历或累加同一批次的历史修订。状态计数按批次 ID 计算，每个部门/类型候选单元由去重的 `UNION` 构成。

## 候选缺陷与反驳

**候选：** `record_ids uuid[]` 本身没有数据库级元素唯一约束；若绕过应用服务直接插入重复 ID，SQL 的 `cardinality` 会重复计数。

**反驳：** 当前对外写路径由服务规范化并拒绝重复 ID；提交、状态迁移、修订写入和审计在一个事务内完成。没有普通业务端点允许直接写 `department_submission_revisions`。因此这个候选需要特权数据库写入绕过受审应用路径，不能据此认定当前面向用户的提交链路有可达缺陷。应把直接数据库篡改排除在本次范围外；若未来增加批量导入修订或其他写入方，再评估数据库数组约束或规范化子表。
