## 1. 已确认决定与现状

- 复用现有账号、系统角色、组织角色和权限体系。老师使用现有普通成员账号，组织角色增加“老师”；不建立独立教师账号体系，不因专业、年级或班级创建角色。
- 老师默认对阶段二、三配置查看能力，管理员可通过模板或个人例外调整；阶段四学生完成前置工作，老师完成处分确认等后置工作。
- 老师可查看、下载已经定稿通报对应的完整 Word/Excel，即使包含其负责班级以外、全年级的数据。文件不按老师负责班级裁切。
- 班级是老师负责范围的最小颗粒度，可覆盖同年级不同专业、同专业不同班级。
- 当前分支 feat-0.1-3；评估时存在用户已有 .env.example 修改，本方案不修改它。
- 当前权限服务已有系统角色、组织角色、部门映射、个人例外和动作鉴权；检查、通报具有独立动作。最新项目状态记录通报唯一维护部门及部门默认权限本地实现，不能据此认定目标环境已部署。
- 当前个人权限规则明确禁止部门、班级、年级范围。老师班级责任关系需要新增明确规则，但不放开学生个人权限范围，不改变原学生部门权限语义。
- 技术方案已提出 PostgreSQL 任务表及 worker。本文建议沿用方向，不将其当作已交付通知能力。PRD 当前 MVP 排除面向学生个人的通知；本次先面向系统操作账号，不自动扩大到被检查学生本人。

## 2. 目标与非目标

目标：在同一账号体系中支持老师只读检查与通报、按班级处理处分；让待办、截止提醒和结果通知可靠到达责任账号，并可追踪失败。

非目标：独立教师系统、课程任课关系、通用审批平台、自动处分、自动定稿、面向全体学生的消息平台；首期不引入 Redis、RabbitMQ、Kafka，不接入未经批准的外部发送渠道。

## 3. 老师账号及权限需求

### 3.1 统一角色及权限配置

只在现有组织角色中增加“老师”。账号、系统角色、登录、个人例外和权限计算均复用现有系统。默认权限配置增加老师模板或老师 Tab，不建设独立教师权限体系。老师无需虚构学生会部门；学生原有部门与岗位配置保持。

老师默认模板配置二、三阶段查看及四阶段所需后置动作。管理员可修改模板，也可在个人账号增加权限或取消权限，按现有允许/拒绝规则计算最终权限。默认只读不是角色权限上限；不增加老师动作白名单、不按身份锁死写操作、不要求额外教师签署资格。页面与 API 都根据最终权限判断可用动作，再校验业务状态和数据范围。

### 3.2 负责范围

账号配置增加负责年级、专业、班级。一个条件内取交集，多条条件取并集：年级＋专业表示该年级该专业；指定班级则到班级。一个账号可负责多个范围，同班可有多位老师，不因此创建更多角色。页面展示覆盖班级，便于核对。按年级或专业配置随基础数据变化匹配，按班级配置则只匹配指定班级。

范围配置只回答“有权限后可以操作哪些数据”，不授予动作。沿用现有权限服务，把范围应用到相关业务查询；不另建授权引擎，不改变学生原有部门范围规则。

### 3.3 默认模板与全量文件

| 能力 | 老师初始配置 | 后续调整 |
|---|---|---|
| 二阶段检查查看 | 开启，按负责范围 | 模板或个人账号调整 |
| 二阶段录入、导入、提交、审核等 | 不开启 | 可按现有权限机制增加 |
| 三阶段查看 | 开启 | 模板或个人账号调整 |
| 定稿通报完整 Word/Excel 查看下载 | 开启，全量文件 | 不受负责班级限制；撤销该权限后不可访问 |
| 三阶段编制、修正、审核、定稿等 | 不开启 | 可按现有权限机制增加 |
| 四阶段处分确认等后置动作 | 按最终流程配置 | 模板或个人账号调整 |

定稿文件全量访问是资源动作的范围语义，不是老师身份绕过鉴权。结构化明细是否按负责范围仍待审查；其他状态、文件可用性、版本冲突等业务校验继续有效。

### 3.4 页面及权限解释

共用登录、工作台、导航与业务页面。现有默认权限页面增加老师配置，现有个人账号页面配置权限增减及负责范围。有效权限详情显示模板来源、个人例外及范围。必要时单独 Tab 隔离配置内容，不复制一套页面和权限引擎。

## 4. 阶段四处分协作需求（流程建议，需审查）

### 4.1 职责及状态

建议流程：学生准备材料 → 提交老师 → 老师确认／退回补充／不予处理。退回后学生补充并重新提交；确认后记录不可直接覆盖，通过更正流程留存新版本。

建议状态：草稿、待老师确认、退回补充、已确认、不予处理、已撤销（仅用于经批准的后续更正流程，首期可不开放）。老师“确认”究竟表示校内正式处分生效，还是提交正式处分流程前的业务确认，必须在开发前明确；未确认前不得以系统按钮替代正式程序。

学生只处理其有权限的前置案件：准备证据、拟议说明、提交、按退回意见补充；不能确认自己的或他人的处分。学生范围建议来自现有经办部门及案件经办关系，不能因为有检查查看权就看到所有处分。老师可查看职责内材料并执行获授动作；退回、不予处理、确认均记录意见、操作者、时间、版本及依据。

### 4.2 案件与依据

案件保存学生引用、班级快照、期间、来源检查记录/定稿通报版本、证据引用、建议结果、规则版本、经办人、处理人、状态和版本。规则匹配只能生成候选，不自动确认处分。累计周期、去重方式、有效记录状态、阈值和更正重算需要单独冻结，不能从既有历史样例推断。

提交时固化材料版本，学生不能在老师确认过程中静默改动。来源更正后将相关待办案件标为需复核，阻止以过期依据确认；已确认案件提示有后续更正，不自动撤销或覆盖历史决定。

多位老师负责同班，建议首期支持一位有相应权限的账号处理即可，以版本冲突防止重复确认；待办对有相应权限的账号可见，处理后对其他人同步结束。若要求指定老师签署，增加案件处理人字段即可，不新增角色。无符合条件老师时，提交明确提示并进入管理员配置待办，不静默丢失案件。

## 5. 通知功能需求

### 5.1 三类对象

- 待办：需要动作的业务工作，是否完成由业务状态决定，已读不等于完成。
- 通知：状态变化或处理结果，具有未读/已读状态。
- 投递任务：后台发送工作，记录待发送、执行中、重试、成功、终止等技术状态；不等于业务已办理或用户已阅读。

站内消息为首期必达记录，工作台呈现待办和未读数；初期使用现有 TanStack Query 定时刷新与窗口聚焦刷新。后续必要时加入 SSE，实时连接不作为消息可靠性保障。

### 5.2 事件清单

| 触发场景 | 接收人 | 行为与关闭条件 |
|---|---|---|
| 部门应交记录临近截止、逾期未交 | 对应部门有权经办人/负责人 | 按应交单元提醒；完成提交后关闭提交提醒 |
| 已提交待部门确认 | 有权部门负责人 | 确认或退回后关闭审核待办；不因提交而关闭全部流程 |
| 部门退回、重新提交 | 原经办人／负责人 | 退回附原因，重新提交更新原待办 |
| 应交齐备可编制通报 | 唯一维护部门有生成权限账号 | 每个周次及来源版本去重；来源变化后重新计算 |
| 通报待审核、退回、待定稿 | 对应动作有权账号 | 随业务状态完成；不自动审核或定稿 |
| 定稿成功 | 有查看权的相关账号、老师 | 发定稿结果通知；文件未生成时不得称可下载 |
| Word/Excel 生成完成或失败 | 请求人/维护责任人 | 成功提供鉴权链接，失败提供可恢复提示；老师不获重试权限 |
| 定稿更正版本形成 | 相关查看者及涉及案件处理人 | 指明版本变化；处分依据另行复核 |
| 处分提交、退回、重新提交 | 有相应权限的账号／学生经办人 | 绑定案件版本，业务处理后关闭 |
| 处分确认、不予处理 | 有权经办人及相关老师 | 结果通知，避免在群聊披露个人处分细节 |
| 处分待办超时、老师移交或无接收人 | 配置的责任人/管理人 | 升级或转派，记录原因 |
| 注册待审核、权限/负责班级变化 | 管理员／本人 | 待审核待办或变更通知，不能包含密码、令牌 |
| 后台任务持续失败、模板不可用 | 维护账号 | 合并告警并支持人工重试，业务用户不接收内部错误 |

时间提醒依赖明确的应交计划、截止时间、时区和例外日。首期建议截止前一次、逾期每日摘要；具体时点、重复次数、升级对象由管理员配置并审查确认，不能凭空推断现有截止规则。

### 5.3 消息中心规则

支持未读/全部、业务类型筛选、标记已读、全部已读、跳转业务。待办单列，展示截止时间、当前状态及处理入口；读消息不能完成待办。同一业务重复提醒合并，展示最近提醒时间和次数。业务处理、取消、换版本后停止旧提醒。

用户只能访问自己的消息；读取消息正文、跳转资源和下载文件均重新鉴权。范围撤销后，历史消息可保留无敏感摘要和审计关联，但不得继续暴露原业务详情。站外消息仅含最小摘要及登录链接；发出后的外部内容不可撤回，因此不得包含敏感证据、学号和处分详情。渠道偏好不允许关闭必须留存的站内待办。

### 5.4 全局消息页与阶段四接入（2026-11-22）

所有已登录的有效账号从公共顶栏铃铛进入独立的「消息中心」页面（路由 `/notifications`），工作台继续提供待办摘要。铃铛展示本人未读数；页面支持分页、未读筛选、按业务分类、单条已读及全部已读。打开消息后可跳转对应业务页；已由他人办理、来源换版或权限收回时，分别展示已处理、已失效或无权查看。未读数查询失败应显示加载失败；跨页标记全部已读以操作时的消息边界为准，保留随后到达的新消息。

| 建议批次 | 事件与接收人 | 消息行为 |
|---|---|---|
| 首批：组织和授权 | 账号归属部门增减、组织角色变更、个人授权授予、调整或撤销 → 受影响账号本人 | 同次保存合并为一条，说明变更项目、生效日期，并链接本人可见的权限说明。未来生效的配置明确显示日期。修改部门模板只影响后续授予，不能据此通知历史快照持有人其权限已变。 |
| 后续：处分 | 新的待确认档位 → 当前有处分确认权且责任范围匹配的老师；作废或替换 → 原接收人收到最小状态摘要 | 成功写入站内收件记录作为站内投递凭据。无合格接收人时提醒管理人核对责任范围。升档关联旧延迟记录，换版终止原提醒。 |
| 后续：时效和责任交接 | 授权到期、责任范围调整 → 本人；涉及未结事项 → 重新核对责任人的管理人及新经办人 | 到期由可补扫的定时任务触发。转交后旧入口停止办理，新责任人收到待办。接收人数、转交、送达和阅读均不改变待处分记录的截止时间。 |
| 后续：审核及通报 | 注册待审、部门退回、通报待审核、定稿或更正 → 当前责任人、原经办人或相关查看者 | 优先接入有明确接收人、可追溯业务版本和有效落点的事件。审批提醒在业务办结后关闭；结果消息可继续查询。 |

首批验收覆盖业务事务回滚后无消息、重复事件每人仅一条、并发到达时已读数正确、本人消息与他人隔离、撤权后列表摘要及详情均不泄露学生信息、离线后重新登录仍能看到消息。先投产本人收件箱及组织变更事件，再将其接入处分事项；真实角色验证送达、打开、办理和归档后，再启用自动确认。处分流程与事件名称采用[阶段四评论整合稿](2026-11-15-phase4-discipline-review.md)。

## 6. 技术方案

### 6.1 总体结构

沿用 Go 模块化单体、PostgreSQL 和现有 React 前端：业务事务写业务数据及事件记录 → worker 消费事件 → 生成账号待办/站内通知 → 可选渠道投递。定时调度器基于数据库应交和待办状态生成提醒事件。

业务事务与事件必须同库同事务提交，避免业务成功却没有通知事件。失败投递不能回滚已经完成的处分确认或通报定稿。采用至少一次执行，靠业务唯一键实现幂等，不承诺跨外部渠道严格恰好一次。

### 6.2 最小数据模型

- account_responsibility_scopes：账号负责的年级、专业、班级范围及版本。
- discipline_cases、discipline_case_versions/actions：处分案件、材料版本、状态轨迹及审计关联。
- notification_events：业务事件 ID、类型、资源 ID、资源版本、产生时间、最小载荷及处理状态。
- notifications：接收账号、事件、类别、标题、受控摘要、资源引用、已读时间；唯一约束避免同一事件向同一账号重复建消息。
- business_tasks：责任账号/资源、动作、期限、状态、资源版本及去重键；业务状态是完成依据。
- notification_deliveries：消息、渠道、状态、尝试次数、下次执行时间、租约期限、错误类别及供应商回执。
- reminder_rules：场景、时区、触发时间、重复/合并/升级规则；首期只开放已实现的固定场景。

任务重试数据与业务审计分开保存，避免把不可变审计当任务队列。保留期限和归档策略需要结合实际容量确定，不无限保存敏感载荷。

### 6.3 worker 与可靠性

用 PostgreSQL 行锁/跳过已锁任务并发领取，短事务领取后在事务外投递，使用租约与执行令牌防止旧 worker 覆盖新执行结果。退避重试并设置上限、死信/失败列表与人工重试。定时任务采用数据库去重键避免多个实例重复调度；停机恢复后补扫仍有效的截止提醒，不一次性轰炸历史消息。

建议去重键由业务资源、版本、场景、接收人、提醒窗口构成。发送前再核对权限、责任关系和业务是否仍待处理，过期提醒标记失效。处理顺序按资源版本判断，晚到的旧事件不能重新打开已经完成的待办。

外部调用超时可能已成功，优先使用渠道幂等键；渠道不支持时接受潜在重复并做频控。系统记录投递成功只表示渠道接受，不表示用户阅读。

### 6.4 权限与查询改造

现有 permission 服务继续统一计算动作权限；老师班级关系作为资源范围约束下推 Repository SQL。不得先加载全量再过滤；分页总数、聚合统计、筛选选项也使用相同范围。

定稿文件下载执行独立分支：有效账号及文件查看动作 + 报告版本已定稿 + 文件属于该版本且可用，允许完整文件；不附加负责班级限制。草稿文件、内部原始导入文件和证据附件不能复用此全量许可。下载沿用受鉴权端点，不公开对象 key；撤权后新请求拒绝。

多班级混合的公共区域/宿舍记录首期建议仅在全部责任班级都获授权时展示原明细，或提供专门脱敏视图；具体语义待审查。禁止用“有任一班级重合”直接泄露整条混合记录。

### 6.5 接口与前端边界

建议在 /api/v1 下增加老师班级分配、处分案件与动作、本人通知、本人待办接口；管理端提供失败投递查询和受控重试。列表沿用 items,total,page,pageSize；更新范围和案件动作带版本；重复请求有幂等/状态保护。

前端端点集中 shared/api，领域模型在 entities，通知用例在 features，页面在 pages；沿用统一 HTTP client 和 TanStack Query。业务页面不直接操作队列表。消息弹窗只是即时反馈，不能替代持久化站内消息。

## 7. 开源及行业方案对比

| 方案 | 可借鉴能力 | 对本项目建议 |
|---|---|---|
| PostgreSQL 任务表 + Transactional Outbox | 原子写业务与事件、后台重试和幂等消费 | 首期首选架构，契合现有技术方案，无新消息中间件 |
| River（Go + PostgreSQL） | 事务入队、任务执行与唯一任务 | 优先做技术验证的库候选，可减少自行维护任务调度；新增依赖需批准 |
| Novu | 通知工作流、站内收件箱、多渠道、偏好 | 借鉴产品模型；目前不直接部署完整平台，避免额外系统与权限同步 |
| Redis/Asynq 或独立消息中间件 | 独立任务处理或事件分发 | 暂不引入；明确吞吐、数据库压力或跨服务需求后再评估 |

River 的唯一任务不意味着只执行一次，仍需消费幂等。消息队列解决后台任务运输，不负责确定谁有权收到消息，也不承担处分状态机。首期可用现有数据库任务设施（如核实可复用）或小范围 worker 实现；采用 River 前验证事务接口、数据库迁移、失败恢复、许可与运维兼容，不在本方案中直接锁定依赖。

- River 项目：https://github.com/riverqueue/river
- River 事务入队：https://riverqueue.com/docs/transactional-enqueueing
- River 唯一任务与至少一次执行：https://riverqueue.com/docs/unique-jobs

## 8. 影响范围与兼容迁移

影响账号角色配置、权限解释及缓存、检查查询、通报索引与下载、工作台、处分新模块、后台任务与通知中心。现有角色代码、学生权限、通报唯一维护部门和历史定稿快照保持。

迁移只追加；不自动把现有账号批量转换老师，不自动授权全班级。老师角色及动作初始化后由管理员明确分配。先部署兼容数据库及服务端，再启用老师账号入口和通知；用功能开关控制新场景，不让开关绕过权限。停用 worker 时保留未处理事件，恢复后续跑。角色/权限变更须审计及使缓存失效。

不能复用已停用的课程教师/排课关系作为班级责任数据，也不能从班主任显示姓名推断账号身份。基础数据若已有班主任字段，只能经管理员核对后建立明确账号关联。

## 11. 现有实现兼容性核查：无部门账号与扩展写权限

本节是 2026-11-14 当前分支源码核查，补充并限定前文“复用即可”的表述：产品配置仍然简单，但现有系统并非纯动作授权，存在系统身份、部门归属、岗位资格等额外判断，必须逐项处理。未执行运行环境验证。

### 11.1 已核实事实

- 无部门不会自动变成管理员。HTTP 层根据 account.SystemRole 显式构造 IsAdmin/IsMember；permission.Effective 也显式判断 ADMIN 才授予配置查看、基础数据管理、字典管理。
- AssignUserRole 当前要求 DepartmentID 非空，老师无部门的岗位分配首先就会失败。
- 普通成员新增记录经过 ResolveEntryDepartment，要求有效主部门；无部门返回 ErrScopeMismatch。即使有 INSPECTION_ENTER 也不能解决归属校验。
- 管理员新增走 ADMINISTRATOR 归属，不能在新增时任意指定部门；这是系统角色驱动的独立暂存及后续归集机制，不是空部门的通用默认值。CanRouteOwn 目前仅为 ADMIN/超级管理员打开。
- 普通成员提交批次要求主部门非空且与批次部门一致；审核的仓储路径同样检查主部门。批次审核是整批原子操作，不能只审核一个混合批次里老师负责的几个班级。
- 通报个人授权写入、有效权限计算及可授予动作目录都检查维护部门资格；ADMIN 有明确例外。无部门 MEMBER 老师不能仅靠添加 REPORT_CORRECT 完成授权。审核、定稿等还有负责人资格；定稿更正又在 reporting 服务检查管理员或部长/副部长身份。
- 个人规则运行时清除 ClassID/Grade/DepartmentID，现有授权不能直接承载老师班级范围。只加前端筛选会造成详情、统计、修改和导出的范围绕过。

### 11.2 动作影响及必须补齐的业务语义

| 获授能力 | 按当前实现的结果 | 改造时必须解决 |
|---|---|---|
| 添加记录 | 无部门 MEMBER 被归属校验拒绝 | 新记录落哪个业务归属、谁提交、谁审核、如何计入应交及通报 |
| 导入 | 必须和手工录入共用同一归属规则；当前链路需完整回归 | 上传预览、确认入库、取消/回滚均校验范围，不能只改新增接口 |
| 修改记录 | 动作权限之外仍有状态、归属及锁定规则 | 班级范围应用于原记录及修改后的目标；不能改班级绕过权限；已锁定数据走既有修正流程 |
| 提交/审核 | MEMBER 被主部门约束；审核整批 | 授权审核的对象是整个批次，混合班级不可静默部分确认；零记录回执也没有可供班级过滤的记录 |
| 修改通报草稿 | 非维护部门个人写授权会被拒绝或不生效 | 保留唯一维护部门作为责任归属，同时支持明确授权账号协作，调整现有资格门禁 |
| 定稿后更正 | 另有身份与 CanReviseFinalizedReport 门禁 | 不能只开放草稿修正按钮；明确是否沿用一个动作覆盖更正或拆已有能力，版本和审计保持 |
| 审核/定稿整份通报 | 当前还有岗位资格 | 整份操作作用于全量版本，不能以班级筛选掩盖全量影响，授权界面必须说明 |

老师获授写权限后可能与学生修改同一资源，沿用乐观锁、事务和冲突提示；顺序发生的两次修改仍可成立，应通过历史版本和变更理由追踪，不额外按老师身份禁止。老师修改已定稿通报仍不能覆盖历史版本。

### 11.3 最小改造方向与待审查选择

保持账号为 MEMBER，新增老师角色和模板。不能通过改成 ADMIN 或将 IsMember=false 来省去部门校验，否则会同时带入系统管理默认权限、管理员记录归属及审核例外。

将现有与身份绑定的业务能力判断调整为明确授权后的可执行判断；不移除状态、版本、审计和数据范围校验。维护部门继续只有一个，额外获授的账号作为协作操作者，不新增第二个维护部门。此处调整的是已有“非维护部门不得获授”规则，需要在实施文档明确替代范围，不能暗改其他学生账号的现有默认值。

无部门录入有两种真实可落地选择，尚未替用户决定：
1. 录入时选择业务归属部门：无需老师成为该部门成员，但需明确可选归属并复用部门提交审核链路；不得自动计为已完成部门应交。
2. 复用独立记录后归集路径：将现有管理员专用路径适配成获授权账号可用的业务能力，明确暂存记录提交到部门还是独立学院批次；不能仅写 NULL 部门后结束开发。

班级范围与整批审核、整份通报操作不能直接等同。建议细粒度记录查看/修改按负责范围；批次审核与整份定稿的授权需明确覆盖整个对象。若只授予班级范围，则不允许部分范围确认整个混合批次，可先按业务规则拆批次；不能悄悄把个人授权解释为全校范围。选择整份操作时界面展示影响范围，保留现有二次确认。

通知接收人必须由最终可执行动作和资源范围计算，不能只按“老师”“部长”名称或 department_id 查找。尤其要覆盖无部门录入待归集、整批审核、协作修正通报、撤权后的待办转移；已读不代表提交或审核完成。
