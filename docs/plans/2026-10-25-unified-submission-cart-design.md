# 统一待提交清单与 Excel 导入批次选取设计

> 状态：2026-10-25 已实施并完成通用提交流程的隔离验收。已新增权限过滤的候选记录、本人已确认导入批次及批次当前记录查询，并在五类执行检查共用的提交操作中加入统一临时清单、核对和最终确认。后端 `go test ./...`、`go vet ./...`、`go build ./...` 及前端全量 Vitest（76/76 文件、414/414 项）、`pnpm lint`、`pnpm build` 通过。Chrome 156、一次性 PostgreSQL/MinIO、真实 API/Vite 的 `department-submission`（24 项）和 `late-return-import`（20 项）浏览器套件通过，覆盖本人 Excel 批次选取、加入同一清单及最终提交；浏览器和清理错误均为 0。五类页面并未逐一完成全套混合来源/角色矩阵，目标环境未加载。适用当前五类执行检查：到课率、无机课堂、早锻炼/早签、宿舍卫生、晚归。教室卫生、公共宿舍卫生沿用现有能力，本次不扩大其业务验收范围。

## 1. 目标与已确认规则

委员从当前检查业务的记录列表，或从自己以前确认入库的 Excel 导入批次，挑选记录汇入**同一张临时待提交表**。委员在表中检查漏选和多选，点击最终确认后，系统才创建一个部门提交批次，交给有权审核的部长、副部长或指定审核人。两种选取方式不产生不同的提交路径；一个提交批次可以包含手工记录及多个 Excel 导入批次的记录。

防重复规则按**业务记录 ID**执行：一条记录首次提交后，不能进入任何新的待提交清单或新的部门提交批次。若原部门提交批次被退回，只能在**原批次**修正和重提，保留同一个 `department_submissions.id`，追加不可变修订；退回记录仍不能进入新清单。原样重提继续允许。确认、锁定和已删除记录均不能作为新提交候选。

这里有三种不同的“批次”：`import_batches` 追溯 Excel 来源；抽屉中的待提交清单只是浏览器内尚未提交的选择；`department_submissions` 是最终审核对象。它们不默认一一对应。现有零记录回执是另一种显式 `ZERO_RECORD` 提交种类，不向记录清单添加虚构记录。

## 2. 当前实现与差距

- 已有导入批次、导入行和业务记录的关联：`import_rows.record_id`、`inspection_records.import_batch_id`。确认入库后生成 `DRAFT` 记录；不能直接把未确认 Excel 预览行拿去审核。
- `POST /api/v1/department-submissions` 已接收同一学期、周次、检查类型和部门/校级归属的一组 `{id, version}`，以幂等键、逐条权限和版本检查、事务及审计创建一次提交。仓储要求 `DRAFT` 且 `submission_id IS NULL`；更新也重复检查这些条件。并发选中同一记录时只能有一次成功。
- `POST /api/v1/department-submissions/:id/resubmit` 已要求原批次、原记录集合及 `RETURNED` 状态，追加修订并保留不可变历史。前端现有“提交所选草稿”只取业务列表当前选择，确认弹窗仅显示条数；导入 API 只能按已知批次 ID 查看，尚无供提交界面检索历史批次及其**当前**记录状态的列表。
- 本设计优先补查询、选择、复核和错误反馈。首次提交与原批次重提继续走各自已有的权威接口，不另造按 Excel 文件直接提交的写接口。

## 3. 委员交互

### 3.1 单一抽屉

在五类检查业务页面的工具栏提供“准备提交”入口，打开宽抽屉。抽屉顶部固定显示当前学期、周次、检查类型和归属部门/校级；缺少明确归属时要求选择，不能把列表中空部门筛选推断成提交目标，也不能默认取第一个学期或周次。若业务上下文改变，已选记录必须先清空并提示用户，不把不同范围混在一个提交批次。

抽屉内提供两个**添加控件**，都向下方同一张待提交表添加记录：

1. “从记录添加”：服务端分页、检索、按业务字段筛选；逐页勾选并持续累积选择。页面“全选”只选当前页可提交记录，文案须写清范围，不得把前端当前页误称为全部筛选结果。
2. “从 Excel 批次添加”：按当前范围展示自己已确认的导入批次，显示原文件名、上传/确认时间、总导入数、当前可首次提交数、已提交数及不可用数。展开批次，按**现存业务记录**分页显示 Excel 行号、关键业务字段、状态和不可选原因；可添加整批可提交记录，或只勾选部分记录。一个批次可以分几次选出不同的尚未提交记录，但此前已提交的记录不能再入新批次。

待提交表按记录 ID 去重，展示姓名/学号等最小必要字段、业务字段、来源、导入批次/行号以及移除操作。手工与 Excel 来源共同排序、分页和计数。表头固定展示“待提交 X 条；当前范围仍可提交 Y 条”；Y 来自同一权威候选查询，便于委员检查遗漏，但不把 Y 全部自动加入。移除仅从临时清单删除，不修改业务记录。支持清空清单；关闭有未提交内容的抽屉时提示将丢弃选择。临时清单只放组件内存，不写 URL、浏览器持久存储或服务端草稿表。

### 3.2 最终核对与提交

点击抽屉底部“核对并提交”先刷新所选记录的当前版本和资格。若有失效项，在原表逐条标出“已提交/被修改/权限变化/已删除”等安全提示，要求移除或重新加载；不可静默跳过。全部有效时显示最终确认区：范围、条数、手工/Excel 数、涉及导入批次数，以及可展开的完整待提交表。委员确认“本次无遗漏和多选”后再点击“确认提交”。只有此时调用已有 `POST /department-submissions`；成功后展示新提交批次编号/状态，并刷新业务记录、批次、工作台和周汇总缓存。

“核对”提高可见性，不代替最终服务端校验。两次点击之间记录仍可能变化，最终写事务必须再次执行全部条件。请求超时或响应丢失时保留同一个幂等键重试相同清单；如果清单、范围或记录版本变了，生成新键。成功后清空临时清单。失败时保留选择和已输入筛选，不把失败伪装为提交成功。

### 3.3 审核、退回和重提

提交成功后整个新批次进入 `PENDING_REVIEW`。部长、副部长或指定审核人继续通过现有提交批次视图审核、退回或确认；不按 Excel 来源拆成多次审核。退回时，原记录转为 `RETURNED`，与原 `submission_id` 保持绑定；委员在原批次更正或原样重提，系统增加修订号和记录快照。退回的记录在“从记录添加”和“从 Excel 批次添加”中均显示“已属原提交批次，仅可从原批次重提”，不提供勾选入口。零记录回执继续使用现有显式入口及审核规则。

## 4. 后端契约与数据设计

### 4.1 只读候选接口

建议新增以下 REST 查询，均使用 `page`、`pageSize`、结构化筛选及 `{items,total,page,pageSize}` 响应，响应字段为 `camelCase`：

| 接口 | 用途 | 关键条件 |
| --- | --- | --- |
| `GET /api/v1/inspections/submission-candidates` | 从记录选择，返回当前可首次提交记录及计数 | 必填学期、周次、检查类型、明确部门或校级；可选来源、关键字、业务筛选 |
| `GET /api/v1/imports` | 检索当前用户以往 Excel 导入批次 | 同一提交范围、`CONFIRMED`、`created_by=当前账号`；返回可提交/已提交/不可用计数，不返回对象 key |
| `GET /api/v1/imports/:id/submission-records` | 展开批次，读取确认入库后仍存在的业务记录 | 批次所有权及有效记录读取权限；按当前记录状态给出 `selectable` 与稳定原因码 |

实现时按现有 Gin 路由注册方式检查静态路由与 `:id` 的顺序。候选接口必须使用业务记录当前值，不能用 `import_rows.normalized_data_json` 作为待审数据；Excel 行号只作来源说明。候选记录响应至少包含 `id`、`rowVersion`、必要展示字段、`source`、`importBatchId`、`importRowNo`、`selectable`。导入批次列表的计数来自实际关联的非删除记录，不直接把 `imported_rows` 当成仍可提交数。文件名来自受控文件元数据，不暴露 MinIO key 或下载地址。

三个查询均把有效 `INSPECTION_VIEW`、`INSPECTION_ENTER`、部门/校级、学年、学期、周次、检查类型、班级/年级及显式 DENY 编入 Repository SQL；可见不等于可提交，候选还要满足当前账号可执行提交所需的逐条动作范围。批次创建者条件不代替记录权限。无权资源按项目现行 403/404 策略处理，不返回一个貌似正常的空列表。批次可见范围与提交范围应分别验证，避免跨部门猜测 ID。

### 4.2 写路径与防重复不变量

继续使用现有首次提交接口，提交请求只包含范围、`kind=RECORDS`、去重后的 `{id, version}` 和幂等键；服务端验证非空、ID 无重复、同一归属范围、授权、当前 `DRAFT`、`submission_id IS NULL`、无通报锁、未删除且版本匹配。任一条失败则**整个事务回滚**，不创建空壳提交批次、不改变其他记录、不写成功审计。一次请求中的重复 ID 应明确返回校验错误；与其他请求争用同一 ID 时返回稳定 409 冲突，而不是部分成功。现有检查记录判重约束仍防止同一业务事实被重新录为不同有效记录；Excel 文件名或文件哈希不能代替记录身份和业务判重。

对返回 409 的客户端提供可操作的稳定错误码，例如现有 `VERSION_CONFLICT` 或 `RECORD_UNAVAILABLE`，必要时新增经授权过滤的失效记录 ID/原因摘要。不得回显越权记录的存在或敏感内容。相同幂等键重放必须识别同一请求指纹并返回原提交批次；用相同键提交不同清单必须失败。原批次重提只经 `/:id/resubmit`：校验该批次为 `RETURNED`、记录集合与上次修订一致、每条记录 `submission_id` 指向此批次且版本匹配；严禁将这些记录送到新建接口。所有状态改变、修订快照和审计在事务中提交。

**数据库选择：**现有 `inspection_records.submission_id`、`row_version`、`department_submissions`、不可变 `department_submission_revisions` 足以表达本需求。首版不需要待提交表或新迁移；如果实际 PostgreSQL 的批次计数/展开查询性能不足，再根据 `EXPLAIN` 追加索引迁移，不改写历史迁移。任何“批次全选”都必须在授权的当前记录集合上执行，并在最终写入时逐条重验。

## 5. 前端结构与状态

- 页面只传明确业务范围；统一抽屉放入 `features/department-submission/ui`，候选查询和提交 mutation 用 TanStack Query hook，经端点 client 与 `shared/api/httpClient` 访问 API。领域候选/清单类型进入 `entities/inspection`，不在页面组件散落请求与权限判断。
- 待提交清单以 `Map<recordId, {id,rowVersion,display,source}>` 表示，两个添加控件共用同一 `add` 操作；移除、清空、失效标记只改变本地状态。跨页选择按 ID 保持，后端分页结果不能覆盖已选集合。当前范围变化时清空并提示；抽屉关闭/重开与 React StrictMode 均不带入旧范围或旧批次选择。
- 查询区分别显示加载、空、失败、403；失败保留清单并允许重试。按钮按有效权限显示和禁用，但服务端每次重新鉴权。表格沿用项目 ProTable 的列、搜索、工具栏模式；窄屏只让表格容器横向滚动。文件名和个人信息按既有脱敏/可见范围呈现。
- 成功与失败都更新相关 Query 缓存；收到版本/状态冲突时重新查询候选与清单记录，不自动删除或替换委员选择。导入后从导入结果跳转到“准备提交”时可以带本次批次 ID 打开选取视图，但不能绕过最终核对。

## 6. 验收与实施顺序

1. **只读 API 与 PostgreSQL 证据**：覆盖本人历史批次、混合来源、批次部分已提交、已删除、已退回、越权批次 ID、班级/年级范围和显式 DENY；验证计数、分页、SQL 范围下推及不可选原因。索引只依据实际查询计划决定。
2. **统一抽屉**：五类页面复用同一组件，验证从两种来源添加、跨页保留、ID 去重、部分导入批次选取、移除、清空、上下文切换、首次打开/关闭重开、失败重试及 StrictMode。提交前实际核对表应展示完整已选集合。
3. **首次提交与原批次重提**：实际 PostgreSQL 覆盖两名委员同时提交同一记录、重复点击/响应丢失重试、同键不同清单、混入已提交/越权/旧版本 ID 后零改动、退回记录无法进入新批次、原批次修正或原样重提及修订快照与审计完整性。
4. **真实浏览器闭环**：一次性 PostgreSQL、独立 Bucket、虚构记录，在五类执行检查中至少分别验证候选及提交；覆盖手工+两个 Excel 批次混选、部分选取、委员核对、部长/副部退回、原批次重提、确认、窄屏和失效冲突。不得在真实业务库制造违规记录。记录浏览器版本、真实 API、故障注入和未覆盖项。

前端运行时代码修改后运行 `pnpm lint`、`pnpm test`、`pnpm build`；后端修改后格式化修改的 Go 文件并运行 `go vet ./...`、`go test ./...`，先聚焦再全量。若涉及新迁移，只在一次性 PostgreSQL 验证。部署、目标环境迁移与真实账号角色验收分别记录，隔离通过不等于目标环境已加载。

**完成条件：**委员可以从两处把可提交记录合入同一临时表，核对后生成一个可审的提交批次；已提交记录在所有添加位置不可选，伪造请求和并发请求也不能让它进入新批次；退回只沿原批次重提并产生新修订；五类页面、API、实际 PostgreSQL 与浏览器均有相应证据。

## 7. 范围外

本次不做新的一级“导入”或“审核”导航，不允许按原 Excel 文件直接触发提交，不修改已确认/锁定历史，不把退回记录拆到新提交批次，不在浏览器持久化敏感待提交清单，也不改变零记录回执、周通报统计口径或暂缓两类卫生专项的范围。
