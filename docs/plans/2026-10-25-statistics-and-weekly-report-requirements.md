# 统计与周通报需求基线（讨论稿）

> 状态：需求讨论稿，尚未批准为最终业务规则。
> 日期：2026-10-25
> 目的：在统计、周通报开发前，把现有已确认规则、代码现状和需要业务确认的口径放在同一处。未决项不得直接转成数据库约束、权限或统计公式。
> **同日范围补充：** 本文初稿后已确认晚自习参加周通报，适用部门/周次沿用逐周应交和零记录回执；只展示确认的缺勤事件，不推导到场率或缺勤率。其业务责任部门待确定。本文原“五类”盘点是补充决定前的历史基线，不改变其他未决统计口径。

## 1. 文档用途与结论

本文面向产品负责人、学生会办公室通报负责人及研发/验收人员。它梳理 PRD、页面功能梳理、技术方案和当前代码盘点，不替代这些文档，也不把未决规则默认为已批准。

当前可以作为需求基线的部分：

- 统计服务于通报流程，不设独立一级导航；入口为“通报管理”中的“数据汇总与统计”。
- 当前目标业务范围为到课率、无机课堂、早锻炼/早签、宿舍卫生、晚归及晚自习六类。晚自习只记录确认后的缺勤事件；教室卫生、公共宿舍卫生继续暂停专项开发和验收，未来接入应由检查类型配置驱动。
- 成员按记录批次提交，部门按周汇总。同一周、部门和检查类型可有多个提交批次；退回后沿用原批次并保存递增修订。
- 只有部门已确认的数据默认进入通报。校级数据批次与部门批次分开，分别按周汇总。
- 学生会办公室部长、副部长默认拥有授权范围内的通报汇总、通报内修正、审核、退回、定稿、导出和发布权限；指定管理员按学期、周次、检查类型补充授权。主席团身份本身不自动获得这些权限。
- 同一学期的每个周次生成一份合并周通报；若其依据的数据发生修改，应重新生成整份通报的新版本。
- 存在未完成部门数据时默认阻止生成。只有学生会办公室部长或其指定负责周通报的副部长（学生会办公室通报管理员）在单独获授强制生成权限后，填写理由才可手动执行强制生成；其他业务部门的部长身份不自动获得该权限，强制动作须审计。
- 统计展示指标族及公式暂不冻结，待后续统计规则制定并确认后写入；历史样例只作为核对材料。
- 通报草稿包含平台内结构化数据及其生成的 Word/Excel 产物。数据在平台内修正后重新生成；下载文件不作为数据修改入口，用户可调整副本的格式/样式，但不得改动数据内容。
- 源数据变更后的重新生成默认手动点击；系统可配置为手动或自动触发。自动模式须产生新版本及对应文件，不能覆盖历史版本。
- 通报链路内修正须保留前后值、原因、人员、时间及关联通报，并同步到相应提交信息；只有需要原部门重新核实或补充材料时才退回。
- 定稿后不得原位修改或撤回；修正以关联原通报的更正版本或补充更正记录处理。定稿文件、统计快照、模板版本和审核/修改轨迹必须能复核。

仍需负责人确认的主要业务决定：

1. 各类展示指标族及其分子、分母、重复计数、空数据和处分风险规则。
2. 统计截止时间，以及办公室修正如何同步源提交和部门侧的具体流程。
3. 正式 Word/Excel 内容、附件顺序、发布方式和模板配置在 MVP 的实现粒度。

### 2.2 代码现状

- 当前代码有七类检查记录页面/API；五类导入、部门批次流程、工作台周聚合及五类本地阶段二门禁已有完成记录。目标环境未独立核对，不能据此认定目标环境门禁通过。
- 工作台聚合的是个人待办和部门状态，不等同于按学生、班级、年级、检查类型、周次和学期生成通报统计。
- 当前有只读周汇总服务/API 及“数据汇总与统计”页，按有效 `REPORT_VIEW` 授权汇总周次、部门/校级批次状态和记录数；当前实现调整为部门树形主项、检查类型子项，并新增分页端点读取当前确认修订内的已确认源记录，返回通报展示字段白名单。迁移 026 排除两类暂停卫生检查。此数据预览仍不创建通报版本，也不生成文件；新明细端点和树形界面尚未通过真实数据库/API及浏览器链路验收。
- 当前没有完整的报告对象/版本状态机、统计规则和快照、生成门禁、通报内修正、审核定稿、Word/Excel 通报文件生成或历史通报归档下载闭环。
- 检查记录上的通报关联/锁定预留字段和通报修正来源值不构成已交付能力。
- 当前导入模板能力不等于 PRD 所说的通报正文、附件和明细导出模板管理。

因此，汇总预览是已交付的通报数据入口基线；它不等于完整统计或通报工作流。阶段二验收不能替代本阶段，历史隔离测试也不能证明完整通报已交付。

### 2.3 真实定稿样例核对

样例是一份“第二周日常管理检查通报”Word，正文后附 6 组材料：到课率、教室卫生、卫生检查（包含公共区卫生和私拉电线检查）、晚归、早签、无机课堂。表格字段进一步包括：

- 到课率/无机课堂：年级、班级、应到/实到、缺课同学、课程、班主任、缺课总课时、到课率。
- 早签：年级、班级、应到/实到、缺到人员、班主任、缺勤总次数、出勤率。
- 教室/寝室卫生：不合格教室或寝室、日期、责任人/责任班级、班主任、情况/违纪原因；另有优秀寝室清单。
- 公共区卫生/私拉电线：日期、班级、寝室、责任人/违纪人员、班主任、宿舍楼/楼层或备注。
- 晚归：年级、日期、班级、寝室、晚归人员、班主任、共查寝间数、缺勤率、备注。

该样例比当前已批准的五类范围更广，包含当前暂停专项验收的教室卫生及公共区域/电线检查内容。首期合并通报不能据此默认恢复这些业务；每类是否有可用且已确认的数据，应在通报范围中清楚标识。

重新读取 Word 正文与表格后，修正此前的行数统计：到课率附件表格共 79 个数据行，其中 78 行按“实到 ÷ 应到”四舍五入保留 1 位小数相符，1 行不符；无机课堂附件共 54 个数据行，54 行均相符。到课率异常行展示应到 35、实到 32、到课率 83.3%，按同一候选公式应为 91.4%。因此样例只能支持“实到 ÷ 应到”作为待确认候选，不能作为零异常的权威定义；应到人数来源、精度和异常处理仍需业务确认。早签附件共 54 个数据行，其中 50 行符合“应到人数 × 5 个检查日”为分母、再扣缺勤总次数的候选计算，另 4 行不符；检查日数及异常处理仍需确认。

样例的公共区卫生、私拉电线、晚归三张表只有表头，没有明细行；仅凭该定稿文件无法判断这是“确认无记录”还是“未提供数据”，系统不能据此默认成零条或已完成。正文还列出到课旷课学时、早锻炼缺到次数、卫生/晚归次数的学期累计处分阶梯、三日内说明要求，并引用 2017 年校级规定。PRD 将处分规则配置化列入优化版本，因此首期是否展示处分风险、样例阈值和说明要求目前是否有效，都不能仅凭该文件推定。

**版式与兼容性核对：** OOXML 显示该文件共 18 个 A4 分节，首页纵向、后续横向，共 24 张表；按当前隔离渲染器输出 29 页。文件使用仿宋、仿宋_GB2312、华文新魏、宋体和黑体等中文字体，而本次渲染环境未能正确加载这些字形，导致中文标题和表头显示为方框或空白。部分分页还出现较大留白或表格续页，因此本次 PNG 只能确认大体表格分页，不能作为源文件版式或生成模板通过的证据；生成模板定稿前须在实际使用的 Microsoft Office/WPS 环境复核。

配套定稿 Excel 有 6 张可见明细表：到课率检查情况、晚归检查情况、卫生检查情况、早锻炼情况、无机课堂、教室卫生。字段随检查类型变化，主要记录学生/专业班级、学号、检查或旷课/晚归时间、违纪次数、累计旷课学时、原因/备注、宿舍或负责区域、班主任；工作簿没有公式单元格或汇总页。无机课堂页只有表头、无数据行，不能据此判断该周已经完成检查且事件为零。其他空表同样需要区分“确认零事件”和“未提供/未完成”。工作簿还保留 1 条未核实的外部链接记录，尽管没有公式单元格；未设置打印区域、重复表头或页面缩放。新模板应由平台结构化数据生成，不复制未核实外链，打印布局与空数据状态需要重新确认。

### 2.4 样例字段与当前五类数据模型对照

以下只盘点当前字段和来源，不批准统计公式。通报汇总 API 当前返回周范围内的批次状态及记录数；提交修订保存 `record_ids` 与业务快照，但尚未返回附件明细或计算样例中的班级指标。当前修订快照在提交时固化 `inspection_records` 及到课率/无机课堂、早锻炼、晚归、宿舍卫生关联明细，并由不可变触发器保护；它是有用的源证据，但不是已确认的导出结构，也没有实现报告级字段白名单、统计快照或 Word/Excel 模板映射。报告生成只能读取当前确认修订的不可变快照，再按批准模板和最小必要字段构造版本数据；不得直接把包含个人和内部字段的原始 JSON 透传给接口或文件。

| 当前五类 | 可从已确认记录/主数据取得的字段 | 样例字段及现有缺口 |
| --- | --- | --- |
| 到课率 | 检查记录保存学生、班级、年级快照；共用课程缺勤明细保存课程、教室、日期/时间/节次和缺课学时。 | 可支持缺勤事件明细及按班级汇总事件学时。样例中的应到/实到人数、到课率及无缺勤班级行不是当前缺勤事件记录本身；班级主数据虽有当前 `enrolled_size` 和班主任关联，但没有按学期/周冻结的在籍人数快照或检查完成清单。不能直接把当前班级人数当作历史分母，也不能从没有缺勤记录推出已检查且全勤。 |
| 无机课堂 | 与到课率共用课程缺勤明细，保留学生/班级/年级快照、课程、教室、时间/节次和缺课学时。 | 样例表的事件字段基本可映射；班级总行、应到/实到、到课率及零事件班级仍缺完整检查范围/分母来源。候选比率存在一条样例异常，公式待确认。 |
| 早锻炼/早签 | 每条记录表示学生某日缺勤，保存学生/班级/年级快照和 `absence_count=1`。 | 可按已确认缺勤事件呈现缺到人员、缺勤事件数和日期；样例的应到/实到、出勤率依赖在籍对象、计划检查日数及每个班级是否完成检查。系统没有已确认的周检查日清单或无缺勤班级回执；“五个检查日”仅是对样例的候选检验。 |
| 宿舍卫生 | 记录有宿舍 ID、日期/时间/轮次、优秀/合格/不合格结果、责任班级/学生、原因和说明。 | 可呈现宿舍结果、责任对象和原因，字段方向与不合格/优秀寝室表相符；检查覆盖范围、每类结果是否都必须逐间建记录及未检查宿舍语义仍待确认。班主任可从当前班级关联查找，但不是检查记录中的历史快照；宿舍名称也通过当前主数据解析。 |
| 晚归 | 每条记录保存学生/班级/年级快照、宿舍 ID、日期/时间和备注。 | 可呈现晚归人员和事件时间；样例的共查寝间数、缺勤率需要已检查寝室数/覆盖范围和相应分母，当前记录模型没有该检查覆盖数据。样例相应表只有表头，不能推定实际值或零值。 |

**跨类型数据限制：** `classes.enrolled_size` 与 `head_teacher_id` 是可维护的当前主数据，没有生效学期/周及报告快照；普通检查记录虽保存学生、班级和年级显示快照，但不保存历史在籍人数或班主任快照。课程、宿舍和教室名称通过当前主数据解析，也不能自动代表历史时点。普通检查记录以事件/异常明细为主，零条事件与完成一次检查不是同一状态。生成历史文件前需要在报告快照中保存实际展示的标签及经确认的分母来源。上述差距是实施前的资料依赖，不代表已决定新增哪种业务表或输入页面。

**完整性门禁的代码证据：** 当前 `workflow.Submit` 校验拒绝零条记录；迁移 016 的 `department_submission_revisions.record_ids` 也有 `cardinality(record_ids) > 0` 约束。因此现有部门提交流程无法表达“本周已检查且确认零条异常”，而无提交/无记录也不能据此解释成已完成。迁移中的 `department_inspection_scopes` 只有部门/检查类型级的 `can_enter`、`can_view`、`can_review`、`can_export`、`can_summarize` 等权限开关；没有按学期/周次定义的必交标记或通报应交单元表。仅凭当前批次状态和可录入范围不能可靠判断全院/授权范围是否完整；需要业务确定应提交部门/检查类型集合及零记录确认方式，再设计最小数据模型与页面。

## 3. 建议的需求边界

### 3.1 首期业务范围

- 首期纳入五类当前执行业务：到课率、无机课堂、早锻炼/早签、宿舍卫生、晚归。
- 教室卫生、公共宿舍卫生默认不进入本期统计/通报，也不得显示成“零条记录”或“已完成”。待其业务规则和范围获批后，通过类型配置另行接入，不把类型列表写死在统计规则中。
- 通报以学年、学期、周次为业务时间范围；用户已确认每周一份合并通报。报告标题、类型组合展示和版本命名待确认。
- 个人/班级/年级/宿舍/教室等统计维度仅在该检查类型有对应可信字段时提供；缺少维度时显示“不适用/无可统计数据”，不伪造关联或零值。

### 3.2 输入数据与纳入规则

- 默认仅使用“部门已确认”的检查记录。草稿、待审核、已退回、未重提记录不计入正式统计。
- 同一部门、周次、检查类型可以有多个提交批次；统计必须按完整授权范围汇总这些批次，不能只取最新一批。
- 校级批次单独列示和统计，不并入任一部门。报告范围应说明校级数据是否存在。
- 预览至少展示数据截止时间、已确认记录量、未完成部门/类型、涉及批次数和统计规则版本。
- 草稿生成时记录准确的数据范围与源记录版本。之后发生的数据变化不得无提示地改变已生成草稿或定稿的内容。
- 草稿引用记录在通报流程中受锁定保护。办公室更正必须走专门的更正操作并留痕，不能绕过锁定直接改源记录。

### 3.3 未完成数据与强制生成

- 默认在存在未完成部门或业务数据时阻止生成周通报，并明确列出未完成项。
- 只有学生会办公室部长或其指定负责周通报的副部长（学生会办公室通报管理员）在单独获授强制生成权限后，填写理由才可手动执行强制生成；其他业务部门的部长身份不自动获得该权限。
- 强制生成权限与一般通报汇总/审核权限分开配置，可按用户授予或撤销；服务端必须检查有效权限，不能只依靠按钮显隐。
- 强制生成时，未完成项、操作人、填写理由、时间和报告范围进入报告版本与审计记录；强制生成不能把未确认数据伪装成已确认或零条数据。

### 3.4 汇总与统计页面

页面放在“通报管理”内，建议按以下区域组织：

1. 范围栏：学年、学期、周次、检查类型组合及数据截止时点。
2. 完成情况：按部门和检查类型展示提交/退回/确认批次、记录数和未完成原因；校级批次独立一行。
3. 统计预览：按类型展示指标、统计范围、公式/口径说明、源数据量和空数据状态。
4. 风险与修正：未完成项、异常/重复/缺字段提示、办公室通报内修正轨迹。
5. 操作区：保存或生成草稿；不满足条件时明确说明阻断项及有权人员可执行的补救动作。

统计不另设一级导航；个人待办、部门待审核数和全院通报进度应保持不同口径。

### 3.5 指标展示族待后续规则确认

PRD 已提出统计能力方向，但各类型通报具体展示哪些指标族尚未确认。本节不预设指标清单；待后续统计规则制定时，再由业务负责人确认展示项和口径。下表只列规则制定时需要解决的问题，不构成已批准的指标或公式。

| 检查类型 | 展示指标族 | 后续规则需要明确的事项 |
| --- | --- | --- |
| 到课率 | 待后续规则确认 | 应到人数/人次来源、计数单位、时间范围、重复处理和精度。 |
| 无机课堂 | 待后续规则确认 | 记录与事件的计数关系、多人/多时段处理、范围和排序。 |
| 早锻炼/早签 | 待后续规则确认 | 缺勤计数、跨周归属、是否需要分母及累计周期。 |
| 宿舍卫生 | 待后续规则确认 | 检查范围、分母、复查合并、缺检与无问题的区分。 |
| 晚归 | 待后续规则确认 | 人次/事件计数、同日多次处理、时间区间及重复判定。 |
| 跨类型 | 待后续规则确认 | 是否允许跨类型累计、业务快照维度、隐私范围和排序规则。 |

处分风险展示也属于待确认规则，不因 PRD 提到累计风险就默认采用历史材料中的阈值或自动输出处分结论。

### 3.6 “生成”代表的对象及版本处理（供本轮审查）

为避免把“统计预览”“报告草稿”和 Word/Excel 文件混为一谈，建议按三个层次定义：

1. **数据汇总预览**：只在页面展示统计和完整性检查；不创建通报版本，也不生成可下载文件。
2. **生成通报草稿**：按已确认数据生成一个可编辑、带版本号的结构化通报草稿，包含正文内容、统计结果、附件明细和数据引用范围；同时从同一草稿版本生成供核对的 Word 通报草稿（正文与附件）和 Excel 明细草稿。结构化草稿是数据平台内的权威版本，Word/Excel 是其产物。Excel 工作表和字段布局仍需审查。
3. **生成定稿**：审核通过后固化本版统计快照、正文和附件内容，生成 Word/Excel 定稿文件；只有文件齐全并校验通过后才进入“已定稿”。

源数据变化后，对引用该数据的未定稿草稿显示“数据已变更/待重新生成”提示，不另增通报生命周期状态。数据应先按平台权限和修正流程在系统内修改；已锁定数据走通报内修正流程。默认由有权人员手动点击重新生成**整份周通报**的新版本，并生成与该版本对应的 Word/Excel；系统可配置为自动触发。自动模式同样创建新版本，保留旧草稿和旧文件，不静默覆盖；若存在未完成数据，自动模式仍须阻断，强制生成只能由有权负责人手动填写理由后执行。下载文件不支持数据回写；下载副本可调整格式和样式，但不得修改数据内容，也不替代平台中的权威版本。定稿后的变化仍按更正版本处理。

### 3.7 草稿、审核、定稿和更正

方案文档列出的通报状态为：

未生成 → 草稿 → 待通报审核 → 通报退回 → 草稿 → 已定稿 → 已发布 → 已归档

每次迁移必须校验当前状态、操作者权限、通报范围、版本号并写入审计。审核意见、退回原因和动作时间进入详情时间线。

- 草稿由已确认数据生成，支持 Word 正文草稿、Excel 明细草稿和在线预览。
- 草稿修改或数据更正形成版本；通报内修正应关联源记录及其提交批次，并记录前值、后值、原因、操作者和时间。
- 需要原部门重新核实/补材料时，才执行退回或重新提交；普通录入错误由有权办公室人员按通报更正流程处理。
- 审核通过后进入定稿生成。只有结构化内容、统计快照、模板版本和所需文件均已成功保存并完成校验，才可标记为已定稿。
- 定稿不可撤回或原位编辑。后续修正建立关联更正版本，保留原始定稿及两版文件。
- 发布和归档是不同业务动作；发布渠道、谁可执行、何时归档与是否自动归档待确认。

### 3.8 权限与数据范围

- 通报权限与主席团身份不自动绑定。办公室部长/副部长按既定默认授权，指定管理员按学期、周次、检查类型范围补充授权。
- 强制生成权限单独配置给学生会办公室部长或其指定负责周通报的副部长（学生会办公室通报管理员），需填写理由；其他业务部门的部长身份不自动获得该权限，不得根据一般通报管理权限或前端按钮显示推定拥有该权限。
- 汇总、通报内修正、审核/退回、定稿、导出/发布、归档查看应是可分别检查的服务端动作权限；界面显隐不能代替服务端授权。
- 办公室人员只能读取其有效检查类型、学期、周次和组织/数据范围；查看局部数据时必须标为局部范围，不能展示为全院完成率。
- 归档查询和文件下载必须重新鉴权；下载链接不能公开或暴露对象存储 key。
- 同一人员能否创建并审核/定稿同一通报、部门管理员能否只读本部门最终数据，当前材料未规定，列为待确认。

### 3.9 定稿快照、文件与归档

每个定稿版本至少需要固化：

- 学年、学期、周次、包含的检查类型、统计截止时间和数据范围。
- 每项统计的维度、对象名称/业务快照、指标值、统计生成时间、规则版本。
- 源检查记录 ID 与版本、部门/校级批次及其确认修订；办公室修正前后值和原因。
- 通报正文与附件结构化内容、Word/Excel 文件、模板及其版本、文件大小和 SHA-256。
- 创建、审核、退回、定稿、发布、更正、归档的操作者、意见和时间。

归档查询至少覆盖学年、学期、周次、类型、状态，以及 PRD 列出的学生/学号、班级和部门。具体可检索字段受角色数据范围限制。历史结果必须基于定稿快照，不随当前学生、班级、部门或字典名称变化。

MVP 文件先按 PRD 的核心 Word 正文/附件与 Excel 明细导出；模板标题规则、附件顺序、是否显示某检查项、空数据展示和文件命名的配置范围需要确认。无数据时不得把“未接入”“未确认”和“确认后零条”混为一类。

## 4. 关键未决项与建议

### 4.1 完整性门禁的可选实现口径（待负责人选择）

现有代码把“可录入范围”和“实际提交”分开保存，但没有每周必须提交的范围清单，也不允许零记录修订。若直接把 `can_enter=true` 当作每周必须检查，会把操作授权误当作业务责任，还无法表达临时停查或周次差异。

**通俗解释：**“可录入范围”回答“这个部门有权限录哪些检查类型”；“每周应交范围”回答“这一周哪些检查类型必须交”。例如学习部有权录入到课率和宿舍卫生：若复用录入范围，就表示这两类每周都必须提交；若单独配置应交范围，则可设置本周只要求到课率、下周要求两类，或某周不要求其中一类。当前页面根据录入权限显示的“暂无提交”只是提示性预览，不能据此认定该项已经是每周义务。

当前汇总 SQL 为了显示“暂无提交”单元，会把启用的部门 `can_enter` 范围与当周实际出现的部门提交范围合并，再匹配参与通报的检查类型；这只是预览行构造方式，不是已批准的逐周应交清单。若业务确认每个已配置录入范围每周都必须提交，可将该预览矩阵作为门禁起点；否则应引入独立、可审计的周次应交范围配置。

| 决策 | 方案 | 结果与代价 |
| --- | --- | --- |
| 每周应交范围 | A. 复用当前汇总预览的部门/类型单元矩阵 | 不新增范围配置；但将长期录入授权解释为每周义务，不能表达本周停查、周次差异或校级专项要求。**本轮未选择。** |
| 每周应交范围 | B. 单独配置学期/周次、部门（或校级）和检查类型的应交单元 | 生成门禁读取明确业务范围；可审计配置变更，也支持周次差异。由学生会办公室部长或指定负责通报的副部长管理，使用单独授权。**用户已确认采用。** |
| 确认零记录 | A. 继续禁止空批次，不增加完成回执 | 可以阻止生成，但无法区分“未检查”和“已检查且没有事件”；无法满足样例空表和系统状态的区分要求。**本轮未选择。** |
| 确认零记录 | B. 在现有提交/审核流程增加显式“已完成、确认零条”提交类型 | 零记录也经历提交、审核/确认、版本和审计；数据库只在该显式类型下允许空 `record_ids`，普通数据批次仍必须含记录。沿用现有检查录入权限提交、部门审核权限确认；说明可选。**用户已确认采用。** |

**已确认组合：B+B。** 门禁只对明确配置的应交单元判断状态；缺失、草稿、待审核、退回都算未完成并默认阻断。已确认记录批次和已确认零记录回执均算完成；统计/文件只引用已确认批次，不把待确认数据带入强制生成结果。强制生成按已确认权限和理由执行，绕过未完成阻断但不能伪装或纳入未确认数据。逐周应交范围由学生会办公室部长或指定负责通报的副部长维护，单独授权；零记录回执沿用现有检查录入权限提交、部门审核权限确认，说明可选。

**已确认的后续记录处理（2026-10-25）：** 某周/部门或校级范围/检查类型已有已确认零记录回执后，若后来发现实际记录，允许追加一个实际记录批次；原零记录回执及其确认修订继续保留为不可变历史，不删除、不覆盖，也不把原回执改写成有记录批次。后续完整性判断应同时保留这两项提交历史，并按各自状态呈现。

**已确认的周期默认值（2026-10-25）：** 通报汇总页的学期/周次下拉默认指向系统工作上下文中的当前周（包括有效临时覆盖），并且仅在该周属于当前用户可查看的周期时选中。当前工作周缺失或不可见时不自动选中第一项，保持空选并提示用户手动选择；用户手动切换后不被系统默认值覆盖。

**实现安全条件：** 零记录回执必须是显式的提交种类/完成状态，而不能仅因 `records: []` 就视为有效；应继续经过部门审核/确认并生成不可变修订。当前提交权限主要在逐条记录的 `inspectionAccessSQL` 校验，空数组不会执行该校验；新回执必须增加服务端范围级权限检查（限定学期/周次/部门或校级范围/类型），并在幂等重放时重新鉴权。幂等指纹也应包含回执种类，防止空数据请求与其他完成操作混淆。应交配置管理也必须由服务端校验独立动作权限并审计。

| 优先级 | 待确认事项 | 建议讨论起点 |
| --- | --- | --- |
| P0 | 各类型展示指标族和统计口径是什么？ | 指标清单暂不冻结。后续规则需明确分子分母、计数单位、来源、去重、范围、空数据、精度、排序及处分风险规则；历史样例仅用于校核。 |
| P0 | 哪些部门/检查类型单元必须提交，如何表达“确认零条”？ | 见本节 4.1 的 A/B 选项。当前代码证据说明不能直接把 `can_enter` 当应交范围，也不能以空记录批次表达已完成。 |
| P0 | 通报统计截止时点和草稿过期判断如何定义？ | 生成时保存范围与源记录版本；明确哪些数据变化会使草稿待重新生成，以及截止时点如何展示。已确认重生成默认手动，可配置自动，且保留版本。 |
| P0 | 办公室通报内修正如何反映到部门提交？ | 现有需求要求同步并留痕；需要决定源提交是新增修订、追加修正记录还是修改当前可见值，以及部门端可见/确认方式。历史提交修订不得被覆盖。 |
| P1 | 强制生成权限的范围是否允许限定部门、班级或年级？ | 当前实现按整份合并周通报授权，可按学年、学期、周次和检查类型收窄；部门/班级/年级子范围被拒绝。该范围粒度由“周通报整体生成”推导，仍需业务方确认；生成写接口验收前应冻结。 |
| P1 | 通报正文/说明如何在平台内编辑，哪些内容属于业务数据？ | 已确认数据需在平台内修正；Word/Excel 下载副本只允许调整格式和样式，不得修改数据，也不能回写平台。仍需细化平台内正文/说明的可编辑字段及审核方式。 |
| P1 | 谁审核自己创建的通报？是否需要双人分离？ | 由业务负责人决定同一人是否可完成汇总、审核和定稿；服务端权限模型预留动作分离。 |
| P1 | 处分风险是否属于 MVP？ | 建议首期只展示可复核的累计数据；自动处分风险/建议等规则获批后单独纳入，避免统计页面输出未经批准的处分结论。 |
| P1 | 发布渠道和归档时机是什么？ | 明确系统内可见、下载、公示/外发的动作差别；发布者、撤错方式及自动归档条件。 |
| P1 | Word/Excel 定稿的样式与空数据规则？ | 选定现有材料样例或批准新标准模板，逐类型确认正文、附件、排序、标题、空数据展示和文件命名。 |
| P1 | 报告模板允许谁维护哪些配置？ | MVP 可先由管理员发布版本化模板和受控配置；任意字段/统计公式配置不属于当前默认需求。 |

## 5. 需求冻结后的验收门槛

需求冻结至少应产出一张经业务确认的指标口径表（指标、粒度、公式、分母来源、时间范围、空值、去重、排序）、权限矩阵、状态迁移表和 Word/Excel 样例/空数据约定。之后实现与验收按以下条件核对：

1. **数据范围**：五类范围、部门批次、退回修订、校级批次及已确认状态均按批准规则汇总；越权和局部范围冒充全院结果被拒绝。
2. **公式与快照**：每一指标有可追溯源记录和规则版本；与人工样例逐项一致；基础数据后续改名/转班不改变历史快照。
3. **完整性风险**：未完成部门、强制生成、缺数据、零数据、类型未接入显示不同状态；强制操作要求有权身份、理由和审计。
4. **生命周期**：生成、编辑、提交审核、通过、退回、重提、定稿、发布、更正和归档仅允许合法迁移；并发冲突和重复请求安全失败/幂等。
5. **通报内修正**：源数据、原提交修订、通报版本及提交端可见状态一致；前后值、原因、人员、时间和关联通报可查。
6. **文件与恢复**：同一版本的结构化数据与 Word/Excel 数据内容一致；下载副本的样式调整不回写平台，数据更改必须先在平台完成并生成新版本；文件生成失败不出现“已定稿”，可安全重试；下载按当前权限复核。
7. **角色与浏览器**：使用真实授权矩阵验证办公室、指定管理员、部门管理员、只读用户和越权用户的完整流程；覆盖实际页面交互顺序和失败重试。

2. 指标规则确认后补齐指标口径表、权限矩阵、状态迁移和 Word/Excel 样例/空数据约定，再进入对应实现计划。
3. 五类本地阶段二门禁已有完成记录；后续按“冻结统计规则与检查完整性 → 通报版本/快照及状态机 → 通报内修正 → 页面 → Word/Excel 与归档 → 目标角色验收”拆分实现。目标环境验收需另有当前运行证据。

统计与通报规则可以继续冻结；已交付的数据汇总预览不能表述为完整统计、周通报生成或归档能力。
