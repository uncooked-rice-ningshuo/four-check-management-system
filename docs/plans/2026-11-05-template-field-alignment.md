## 7. 「两项违纪次数一起算」实现方案（**已定为方案 A**）

### 现状

- 每条卫生记录在通报里固定计 **1 次**（`ReportRecordTable.tsx` 中写死 `'1 次'`）。
- 周报汇总表**按检查类型分行**，每行显示「已确认记录」数；宿舍卫生、公共宿舍卫生是两个独立行。
- 提交批次、应交项、零回执都**按检查类型独立管理**，通报定稿会把记录冻结进 `weekly_report_version_records`。

### 方案 A：只合并展示，不动数据与流程（推荐）

- 数据层、提交流程、应交项、快照**全部不变**。
- 在周报汇总表新增一列「卫生违纪合计」：宿舍卫生 + 公共宿舍卫生两行的已确认记录数相加。
- 通报定稿时把该合计值一并冻结进版本快照，保证历史通报口径不随后续数据变化。
- **优点**：不动批次日志与零回执逻辑，风险最低；两类型仍可分开展示明细。
- **代价**：汇总表多一列，两行本身仍各显示自己的数。

### 方案 B：汇总表合并成一行

- 两个类型在汇总表里合成「卫生（宿舍+公共宿舍）」一行，显示合计。
- **代价**：破坏「未完成应交项」「零回执」按类型判断的逻辑；某一类型未提交时无法在表上区分。**不推荐**。

### 方案 C：只在通报正文/导出合并

- 工作台界面不变，仅在定稿生成的通报正文里把两类违纪次数写成合计。
- **代价**：当前 Word/Excel 通报导出本身尚未交付，此方案要等导出功能一起做。

### 结论：采用方案 A

**后续处分通报模块的约束（已确认）**：处分划定依据是「宿舍卫生 + 公共宿舍卫生」合起来的违纪次数，而不是各自单独的数字。因此合计值不能只是前端的一列加法，必须作为**正式统计口径**：

- 在 `reporting` 领域新增聚合：`HygieneViolationTotal(departmentId, period)` = 两类型已确认记录数之和。
- 该值随通报定稿一起写入版本快照，历史通报口径不随后续数据变化漂移。
- 通过 API 暴露（汇总行字段 + 独立查询），处分模块将来直接读取，不重复实现聚合逻辑。
- 前端汇总表新增「卫生违纪合计」列展示同一来源的值。

## 8. 影响面与风险

| 风险 | 说明 |
| --- | --- |
| 到课率改为日期级 | 重复键（班级+学生+日期+规范化节次区间）不含时间，判定逻辑不受影响，但仍需回归批内/库内重复用例 |
